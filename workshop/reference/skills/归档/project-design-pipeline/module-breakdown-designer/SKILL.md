# 功能模块拆解设计师

通过扫描现有设计文档并与用户对齐需求，产出一份覆盖完整、边界清晰、盲区已补的功能模块拆解文档。

## 工作流程

### 步骤 1：扫描设计文档

1. 递归列出项目 `docs/` 目录下的所有文件。
2. 读取所有看起来是设计、架构、需求或功能规格说明的 Markdown 文件。
3. 跳过自动生成的 API 文档、变更日志和会议纪要，除非它们包含功能性需求。
4. 总结发现的关键功能领域、参与者、数据实体和工作流。

> 如果 `docs/` 目录不存在或为空，先询问用户设计文档存放位置，再继续。

### 步骤 2：与用户对齐需求

在产出拆解文档之前，向用户提出 **2-4 个聚焦问题**，以消除歧义并定制输出。根据设计文档揭示的内容，从以下列表中选择最相关的问题：

**项目背景**
- "这是什么类型的项目？（例如：SaaS、AI Agent 系统、电商、内部工具、游戏）"
- "主要用户或参与者是谁？"

**范围与约束**
- "有哪些模块是你已经确定必须包含或必须排除的？"
- "这次拆解是为了 MVP 规划、完整产品范围，还是某个特定阶段？"

**质量优先级**
- "哪个更重要： exhaustive coverage（ exhaustive 覆盖）还是严格的边界清晰？"
- "是否有必须单独列出的监管、合规或安全领域（例如：认证、审计、GDPR）？"

**输出偏好**
- "拆解文档应该只包含业务功能模块，还是也包含基础设施/运维模块（例如：监控、CI/CD、部署）？"
- "你偏好哪种编号方式？（例如：`MOD-01` 类别前缀式，还是 `1.2.3` 层级式）"

记录用户的回答。仅在用户明确表示拒绝回答时使用默认值：
- 默认范围：完整产品范围，包含基础设施。
- 默认优先级：边界清晰优先于 exhaustive 覆盖。
- 默认编号方式：类别前缀 + 两位序号（例如 `PLM-01`、`INF-03`）。

### 步骤 3：从设计文档提取模块

针对文档中发现的每个功能领域：

1. **识别原子模块**：模块必须代表一个单一的、内聚的能力，能够被独立描述、估算和实现。持续分解聚合项，直到每个条目通过"单句职责"测试。
2. **分配标识符**：使用短类别前缀 + 两位数字（例如 `USR-01`、`BILL-05`）。按功能域将模块分组到编号章节下。
3. **为每个模块编写四个核心字段**：
   - **模块名称**：名词短语，2-6 个汉字或 1-4 个英文单词。
   - **核心功能**：一句话描述该模块做什么，而非怎么做。
   - **颗粒度描述**：具体、可测试的行为或约束（例如"支持 5 种策略标签"、"默认 3 个并行版本"）。
   - **设计文档溯源**：该模块源自哪份源文档的哪个章节。使用 `§章节` 记号。

4. **标记模块类型**：为每个模块评估并标记其类型。这是本阶段的关键输出，直接决定下游 `module-spec-writer` 的问答策略：
   - `🔴 核心`：项目特色或差异化功能；设计文档描述不够清晰、存在多种实现可能；涉及复杂业务规则、状态机或关键算法决策；位于用户关键路径上，出错成本高；与多个模块紧密耦合的枢纽模块；技术选型对项目架构有重大影响。
   - `🟢 一般`：行业内常见标准实现（如标准 CRUD、常见认证流程）；设计文档描述清晰，实现路径唯一；存在成熟开源方案或框架可直接使用；不涉及项目核心差异化竞争力。

   **判断时参考以下检查清单**（满足任意一条即倾向于对应类型）：
   - 如果去掉这个模块，项目的核心价值是否受损？（否 → 🟢 一般；是 → 🔴 核心）
   - 这个模块的实现方式在团队内部是否可能产生分歧？（否 → 🟢 一般；是 → 🔴 核心）
   - 这个模块是否有 2 种以上差异显著的可行方案？（否 → 🟢 一般；是 → 🔴 核心）
   - 这个模块是否是用户选择本产品而非竞品的主要原因？（否 → 🟢 一般；是 → 🔴 核心）
   - 该功能是否有广泛认可的行业最佳实践或成熟开源方案？（是 → 🟢 一般；否 → 🔴 核心）

   > **约束**：`🔴 核心` 模块通常应占总模块数的 **30-40%**。若超过 50%，说明判断标准过松，需重新审视；若低于 15%，说明可能遗漏了真正需要严格对齐的模块。

5. **标记歧义**：如果设计文档在同一个名称下描述了两种不同的能力，将它们拆分为独立的模块并注明拆分原因。

6. **强制逻辑/表现分离**：检查每个候选模块是否同时包含"数据处理/状态管理"（逻辑层）和"UI 渲染/视觉呈现"（表现层）的职责。**绝对禁止一个模块同时承担两者。**
   - **逻辑层**：数据获取、状态管理、业务计算、API 调用、路由控制、数据校验、缓存策略等。在前端对应 hooks/services/stores/context，在后端对应 service/data-access 层。
   - **表现层**：UI 渲染、样式/布局、动画/过渡、视觉反馈、响应式适配等。在前端对应 components/pages/styles。
   - **拆分示例**：
     - `用户登录` 若含登录表单 UI + 登录状态管理/API 调用 → 拆为 `登录界面`（表现层）和 `登录认证逻辑`（逻辑层）。
     - `数据仪表盘` 若含图表渲染 + 数据聚合/查询 → 拆为 `仪表盘展示组件`（表现层）和 `仪表盘数据服务`（逻辑层）。
     - `参数配置面板` 若含表单控件渲染 + 参数校验/持久化 → 拆为 `参数配置UI`（表现层）和 `参数配置逻辑`（逻辑层）。
   - 这一原则适用于前后端分离项目中的前端模块划分。后端模块天然属于逻辑层，前端模块则必须区分逻辑层与表现层。

### 步骤 4：交叉检查边界并消除重叠

执行系统性的冲突检查：

1. **将所有模块名称和核心功能通读一遍**（概念上）。自问："这两个模块能否合理地分配给两位不同的工程师，而无需日常协调？"
2. **检测重叠**：如果两个模块共享 >50% 的颗粒度描述，或都声称对同一用户可见结果负责，合并它们或重绘边界。
3. **检测盲区**：如果某个用户工作流存在一个逻辑步骤但没有归属模块，创建一个占位模块并标记它。
4. **强制命名约束**：模块名称不得包含连词（"与"、"及"、"and"、"&"）。将含连词的模块拆分为多个模块。
5. **检测逻辑/表现混杂**：逐模块审查其"核心功能"描述。若描述中同时出现**数据处理动词**（获取、计算、存储、管理、校验、缓存、同步）和**视觉呈现动词**（显示、渲染、展示、布局、绘制、动画），说明该模块跨越了逻辑层与表现层的边界，必须标记为违规并强制拆分。

> **硬性规则**：最终拆解文档中不得存在任何一对模块，使得其中一个模块的核心功能是另一个的子集。要么合并它们，要么缩小父模块的范围。
> **硬性规则**：最终拆解文档中不得存在任何模块同时承担逻辑层与表现层职责。每个模块要么属于逻辑层，要么属于表现层，不可两者兼备。

### 步骤 5：用行业最佳实践补充

将提取出的模块集合与已识别项目类型的常见功能域进行对比。参见 [references/industry-practices.md](references/industry-practices.md) 获取按项目类型分类的检查清单。

对于每个标准域（例如：认证、审计日志、可观测性、导入导出、速率限制）：
- 如果设计文档已经覆盖，确保它以一个独立模块的形式呈现。
- 如果设计文档遗漏了它，但该项目类型通常需要，添加一个**补充模块**，并在溯源列标记为 `🔄 行业补充`。
- 如果项目明确不需要它，在脚注中明确说明排除理由。

### 步骤 6：编写拆解文档

输出一份 Markdown 文件，默认命名为 `功能模块全拆解.md`（或用户指定的名称），保存到项目根目录或 `docs/` 目录。

遵循 [references/output-template.md](references/output-template.md) 中的精确结构。关键格式规则：

- 使用 H2 (`##`) 作为功能域标题（例如 `## 一、项目生命周期管理`）。
- 仅当功能域包含 >8 个模块时，才使用 H3 (`###`) 作为子域。
- 使用 Markdown 表格呈现模块，列名为：`模块编号 | 模块名称 | 模块类型 | 核心功能 | 颗粒度描述 | 设计文档溯源`。
- 在每个 H2 功能域之间插入 `---` 分隔线以增强视觉清晰度。
- 结尾附 `## 附录` 章节，包含：
  - **附录 A**：排除的标准模块及原因
  - **附录 B**：标记为 `🔄 行业补充` 的模块及其理由
  - **附录 C**：已知的边界决策（两个本可合并但保持独立的模块，解释原因）
  - **附录 D**：模块类型判断依据 —— **仅列出被标记为 `🔴 核心` 的模块**。一般模块的判断标准统一（行业常见实现、设计文档清晰、有成熟方案），无需逐条赘述。每条核心模块的理由必须引用判断标准中的具体条目，并结合模块特征说明，禁止空泛描述（如"这个很重要"）。示例：`对应检查清单第 2 条：实现方式可能产生分歧（设计文档仅描述"智能推荐"，未明确是基于协同过滤还是内容推荐，两种方案差异显著）。`

### 步骤 7：交付前自检

在最终定稿前， mentally 运行以下检查清单：

- [ ] 每个模块都有唯一标识符。
- [ ] 任意两个模块不存在 >50% 的功能重叠。
- [ ] 模块名称不含连词（"与"/"and"/"&"）。
- [ ] 每个模块能用一句话描述清楚。
- [ ] 所有前端模块已实现逻辑层与表现层分离，无模块同时承担两者职责。
- [ ] 至少对照了一个标准行业域检查盲区。
- [ ] 每个 `🔄 行业补充` 模块都有简要理由。
- [ ] 文档包含溯源列，能链接回源文档。
- [ ] 每个模块都已明确标记 `🔴 核心` 或 `🟢 一般`，无未分类模块。
- [ ] 附录 D 中每个核心模块都有具体判断依据，引用判断标准条目并结合模块特征说明。
- [ ] 核心模块占比合理（通常占总模块数的 30-40%，超过 50% 需重新审视）。
- [ ] 未暗示任何依赖关系或实现顺序（本文档纯粹是功能分解）。

# 技术栈设计 Skill

## 核心原则

- **交互式决策**：关键技术选型必须向用户提问并提供选项，禁止 AI 单方面决定全部技术栈。
- **需求对齐**：每项选型需明确对应功能需求与约束条件。
- **落地优先**：优先成熟、社区活跃、团队可驾驭的方案。
- **风险可控**：新引入技术必须给出后备方案与迁移成本评估。
- **渐进确认**：采用多阶段输出，用户在每个阶段可纠偏。

---

## 执行流程（5 阶段，必须严格遵循）

### 阶段 1：需求与上下文确认

读取用户提供的功能文档（如有），然后**必须追问以下关键上下文**（至少 3 项，使用 AskUserQuestion 或对话确认）：

1. **团队技术背景**：团队最熟悉的技术栈是什么？（如：主技术栈 React + Python，无 Go 经验）
2. **部署环境**：目标部署环境？（阿里云 / AWS / 自建 / 混合云 / 无偏好）
3. **预期规模**：目标并发用户数或 QPS？数据量级？（如：日活 1k，无高并发）
4. **运维能力**：是否有专职运维/DevOps？（无 / 1 人兼职 / 专职团队）
5. **合规与预算**：是否有数据合规要求（等保/GDPR/数据不出境）或预算限制？
6. **已有基础设施**：是否已运行某些服务（如已有 MySQL、Redis、K8s）？

同时判定场景：
- **情景 A（全新设计）**：用户未提供已有技术栈文档 → 构建完整体系。
- **情景 B（增量更新）**：用户提供了原技术栈文档 → 基于现有架构适配新需求，优先复用已有组件。

---

### 阶段 2：架构模式与关键关节提问

基于阶段 1 收集的约束，在以下关节点**必须向用户提问**（使用 AskUserQuestion，提供 2-4 个选项及各自优劣）。若用户表示"无偏好"，则基于约束推荐并说明理由，等待用户确认。

#### 关节点清单

| # | 关节点 | 提问示例 | 参考文件 |
|---|--------|----------|----------|
| 1 | **前端框架** | 前端框架偏好？是否需要 SSR/SSG？ | `references/decision-matrix.md` §1 |
| 2 | **后端语言** | 后端语言与框架偏好？ | `references/decision-matrix.md` §2 |
| 3 | **数据存储** | 核心数据是否涉及复杂事务/关系查询？ | `references/decision-matrix.md` §3, §4 |
| 4 | **实时通信** | 是否需要服务端实时推送（通知、AI 流式输出、聊天）？ | `references/decision-matrix.md` §6 |
| 5 | **认证方案** | 用户体系复杂度？是否需 OAuth/企业 SSO？ | `references/decision-matrix.md` §7 |
| 6 | **AI 集成** | 是否需要 LLM 调用或向量检索能力？ | `references/decision-matrix.md` §9 |
| 7 | **部署方式** | 运维团队规模？倾向何种部署方式？ | `references/decision-matrix.md` §8 |
| 8 | **架构模式** | 项目阶段与团队规模？单体 or 微服务？ | `references/decision-matrix.md` §10 |

> **规则**：
> - 不是所有关节都必须提问。根据功能需求特征**选择性提问**（如没有实时功能则跳过实时通信）。
> - 每个问题必须附带 2-4 个选项及一句话优劣说明。
> - 用户确认选择后，再进入下一阶段。

---

### 阶段 3：分层方案细化

基于用户已确认的选型，按以下维度逐层细化。若需对比说明，读取 `references/decision-matrix.md` 对应章节。

分层维度：
1. **前端**：框架、构建工具、状态管理、UI 库、测试方案
2. **后端**：语言/框架、API 风格（REST/GraphQL/gRPC）、异步模型、测试方案
3. **存储**：关系型数据库、缓存、NoSQL、对象存储、向量数据库（如有）
4. **中间件**：消息队列、搜索引擎、任务调度
5. **实时通信**：WebSocket / SSE / 长轮询 / MQTT（如有）
6. **安全**：认证、鉴权、传输加密、敏感数据处理
7. **运维**：部署编排、CI/CD、监控告警、日志收集

每项选型标注：
- **核心作用**：一句话说明解决什么问题
- **版本建议**：具体版本号或版本范围
- **需求关联**：引用对应的功能需求
- **变更影响**（仅增量更新）：与现有架构的兼容性说明

---

### 阶段 4：方案确认

以表格形式向用户呈现**完整技术栈概览**（类似下方示例），并列出核心功能的实现要点（接口/数据模型/异步流）。

```markdown
| 技术维度 | 选用技术 | 版本建议 | 核心作用 |
|----------|----------|----------|----------|
| 前端框架 | React | 18.x | UI 交互 |
| 后端框架 | FastAPI | 0.110+ | API 网关 |
| 数据库 | PostgreSQL | 16.x | 主数据持久化 |
```

然后**询问用户**：
- 是否满意当前方案？
- 是否需要调整某些组件？
- 是否有遗漏的维度？

用户确认后再进入阶段 5。

---

### 阶段 5：输出文档

按 `references/output-template.md` 生成结构化 Markdown 技术栈设计文档。

- **情景 A（全新设计）**：创建新文件 `docs/项目名称-技术栈设计.md`
- **情景 B（增量更新）**：全量重写原文档（保留原结构，融入新内容），在头部追加版本记录行

输出完成后，向用户说明文件路径，并提醒："本文档由 AI 辅助生成，建议经技术负责人评审后生效。"

---

## 约束与禁忌

- **禁止单方面决定**：在阶段 2 的关节点未向用户确认前，不要输出完整技术栈。
- **禁止忽略约束**：若用户明确说"团队无 K8s 经验"，不要推荐 K8s 部署。
- **禁止过度设计**：日活 < 1k 的项目不要推荐微服务。
- **变更最小化**：情景 B 下，若现有组件能覆盖新需求，必须明确说"复用现有 XX，无需引入新技术"。
- **中文输出**：本 skill 所有输出文本（含文档内容）使用中文，代码与专有名词除外。

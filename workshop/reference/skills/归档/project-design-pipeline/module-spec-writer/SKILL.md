# Module Spec Writer

基于已冻结的**意图文档**，为功能模块生成两份技术文档：
- **设计文档（瘦身版）**（给维护者看）：技术实现思路、架构权衡、兼容性分析、设计原则兑现
- **落地规范**（给 Code Agent 看）：精确的类型定义、接口契约、状态转换表、异常阈值、可复制粘贴的测试数据

> **流水线关系**：module-intent-writer → 意图文档（冻结）→ module-spec-writer → 设计文档 + 落地规范
> module-spec-writer **必须**以已冻结的意图文档为输入，**禁止**跳过意图文档直接生成技术规格。

---

## 前置检查（硬性门控）

在启动任何工作之前，必须先执行以下检查：

### 检查 1：意图文档是否存在

**标准路径**：`docs/功能设计/[所属分组]/[模块编号]-[模块名称]/[模块编号]-[模块名称]-意图文档.md`

**查找逻辑**：
1. 先按标准路径查找
2. 若标准路径不存在，扫描 `docs/功能设计/` 目录及其子目录，按模块编号和名称匹配查找
3. 若找到意图文档，读取其内容
4. 若找不到意图文档 → **立即停止工作，向用户报告**：
   > "未找到 `[编号]-[名称]-意图文档.md`。module-spec-writer 必须以已冻结的意图文档为强制输入。请先使用 module-intent-writer 生成并冻结意图文档，再进入技术规格编写阶段。"

### 检查 2：意图文档是否已冻结

读取意图文档后，检查文档状态：
- 若文档状态为 `已冻结` 且有明确的冻结时间 → **通过检查，继续工作**
- 若文档状态为 `草稿` 或未标注冻结状态 → **立即停止工作，向用户报告**：
   > "意图文档 `[编号]-[名称]-意图文档.md` 尚未冻结。module-spec-writer 只能以已冻结的意图文档为输入。请先完成冻结授权流程，再进入技术规格编写阶段。"

### 检查 3：意图文档的业务定义与技术可行性初步审查

在继续之前，快速扫描意图文档中的业务约束和验收标准，判断是否存在**明显的技术不可行项**：

- 验收标准中的性能指标在当前技术架构下是否可能达成（如"2 秒内完成"但系统架构明显不支持）
- 业务约束是否与项目技术栈设计文档存在根本性冲突（如要求使用意图文档中明确禁止的技术）
- 状态机的业务定义是否涉及技术上无法实现的并发/一致性要求

**若发现技术不可行项** → 执行**回退机制**（详见下方"回退机制"章节）。

## 工作流程

### Step 1: 收集输入材料路径

主 Agent 的定位职责：找到所有需要 SubAgent 读取的材料路径，不做内容分析。

**输入来源优先级**：已冻结的意图文档 >= 全局设计文档 > 功能模块全拆解表 > 原始设计文档 > 已有规格文档。

#### 1.1 确认意图文档路径

从检查 1 已获得路径。记录模块编号、名称、类型、冻结时间。

#### 1.2 定位全局设计文档

**技术栈设计文档**：
- **标准路径**：`docs/技术栈设计.md`
- **若不存在**：扫描 `docs/` 目录，查找 `*技术栈*.md`、`*tech-stack*.md`、`*技术选型*.md`

**项目结构设计文档**：
- **标准路径**：`docs/项目结构设计.md`
- **若不存在**：扫描 `docs/` 目录，查找 `*项目结构*.md`、`*project-structure*.md`、`*目录结构*.md`

> 若找不到全局设计文档 → 继续执行，但在后续向用户汇报时标注"⚠️ 未找到全局设计文档，SubAgent 将基于意图文档和行业默认方案做决策"。

#### 1.3 定位功能模块全拆解表

**标准路径**：`docs/功能设计/功能模块全拆解.md`

提取当前模块的信息：核心功能、颗粒度描述、设计文档溯源、所属分组。

#### 1.4 定位原始设计文档

根据"设计文档溯源"中引用的文档名，找到对应的原始设计文档路径。仅记录路径，不读取内容。

#### 1.5 定位契约索引与已有规格

- **契约索引**：`docs/功能设计/_contracts.md`
- **已有规格文档**：扫描 `docs/功能设计/` 及其子目录，列出所有 `[编号]-[名称]-落地规范.md` 文件路径

#### 1.6 汇总材料清单

将所有找到的材料路径整理为清单，准备传递给 SubAgent。

---

### Step 2: 调用 SubAgent 进行技术决策

**SubAgent 角色**：技术决策专家。读取全部材料，做出技术上最优的全部决策，标记业务矛盾。

**调用方式**：使用 `Agent` 工具调用 `spec-researcher`，传递以下内容：

```
你是 module-spec-writer 的 spec-researcher SubAgent。
请阅读以下材料，完成技术决策完整报告。

**模块标识**：
- 编号：[编号]
- 名称：[名称]
- 类型：[🔴 核心 / 🟢 一般]

**材料路径清单**：
1. 意图文档：[路径]
2. 技术栈设计文档：[路径 或 "未找到"]
3. 项目结构设计文档：[路径 或 "未找到"]
4. 功能模块全拆解表：[路径 或 "未找到"]
5. 原始设计文档：[路径列表 或 "无"]
6. 契约索引：[路径 或 "未找到"]
7. 已有规格文档：[路径列表 或 "无"]

**任务**：
1. 读取所有材料
2. 完成兼容性审查（与已有规格对比）
3. 做出所有技术上可确定的最优决策
4. 标记所有业务矛盾点
5. 输出《技术决策完整报告》，格式参见 agents/spec-researcher.md 的 Step R5
```

**主 Agent 等待 SubAgent 返回完整报告**。报告必须包含：
- 材料清单（确认所有材料已读取）
- 兼容性审查结论
- 技术边界（已确定的输入/输出类型、依赖、状态机、异常策略）
- 技术决策清单（所有自主确定的决策及依据）
- **业务矛盾标记清单**（需要用户裁决的问题）

---

### Step 3: 审查 SubAgent 报告与业务矛盾处理

#### 3.1 读取并理解报告

主 Agent 仔细阅读 SubAgent 返回的《技术决策完整报告》，重点检查：

- 材料读取是否完整（特别是意图文档和全局设计文档）
- 技术决策是否有明显违背意图文档的地方
- 业务矛盾标记是否合理（是否该标未标、不该标乱标）

#### 3.2 分流：按模块类型处理

**若模块类型为 `🔴 核心`**：
- 即使业务矛盾标记清单为空，也进入 **3.4 轻量级确认**
- 若有业务矛盾 → 先处理矛盾，再进入轻量级确认

**若模块类型为 `🟢 一般`**：
- 若业务矛盾标记清单为空 → 直接进入 **3.4 轻量级确认**
- 若有业务矛盾 → 处理矛盾后进入轻量级确认

#### 3.3 处理业务矛盾（如有）

对于 SubAgent 标记的每个业务矛盾，主 Agent 调用 `AskUserQuestion`：

- **每轮最多 4 个问题**
- 推荐方案放在第一个选项，标注 `(Recommended)`
- 每个问题 `header` ≤12 字
- 先简要说明矛盾的技术背景，再提问

**常见矛盾类型及问法**：

| 矛盾类型 | 问法示例 |
|:---|:---|
| 意图歧义 | "意图文档中'XX'的技术实现有两种解读，请选择：" |
| 基础设施缺失 | "本模块需要 Redis 缓存，但项目结构文档未定义。请选择处理方式：" |
| CAP 权衡 | "本模块涉及强一致性 vs 最终一致性的取舍，请根据业务场景选择：" |
| 性能阈值 | "意图文档未定义具体超时秒数，SubAgent 推荐 30s，请确认：" |
| 冲突裁决 | "本模块的用户状态定义与 M03 存在语义冲突，请裁决：" |

**处理规则**：
- 用户做出选择后，将决策结论补充到 SubAgent 报告中
- 若用户选择"Other"并给出新方案，记录该方案
- 一轮处理不完的，继续下一轮，直到所有矛盾解决

#### 3.4 轻量级确认

**无论是否有业务矛盾，在生成文档前必须输出决策摘要。轻量级确认是纯文本输出环节，禁止调用 AskUserQuestion。**

向用户输出一段**决策摘要**（3-8 句话）：

```
SubAgent 已基于项目设计文档完成技术预研，做出 [N] 项技术决策，
发现 [M] 处需您确认的业务矛盾[已解决 / 待解决]。

关键决策摘要：
- 技术边界：[一句话，如"接收 M01 的 ParsedInput，产出 WorldBuildOutput"]
- 核心技术选型：[一句话，如"CrewAI 串行编排 + Neo4j 持久化"]
- 状态机方案：[一句话，如"IDLE→BUILDING→COMPLETED|FAILED，Neo4j 节点属性存储"]
- 主要异常策略：[一句话，如"LLM 超时 30s/重试 3 次，Neo4j 失败 3 次固定间隔"]
- [若有基础设施引入或重大架构决策，额外标注]
```

**按模块类型区分后续行为**：

**🟢 一般模块**：
- 摘要结尾声明："我将直接进入文档生成阶段。"
- 输出摘要后，**在同一回合内直接进入 Step 4**，不等待用户回应
- 不调用 AskUserQuestion，不暂停等待，不请求确认
- 用户如有异议可在下一回合打断

**🔴 核心模块**：
- 摘要结尾声明："如无异议请确认，我将进入文档生成阶段。"
- 输出摘要后**结束当前回合**，等待用户回应
- 同样不调用 AskUserQuestion——等待用户下一回合自然回复即可
- 用户确认 → 下一回合进入 Step 4
- 用户提出修改 → 调整后重新输出摘要确认

> **为何核心模块仍需等待**：核心模块的 SubAgent 技术决策影响范围大，给用户一个"veto 窗口"。一般模块风险低，直接继续即可，无需增加交互负担。

### 回退机制

> **本机制是 spec-writer 的硬性约束。发现意图缺陷时，无权自行妥协。**

在 Step 1（前置检查）或 Step 3（审查报告）中，若发现以下情况，必须触发回退机制：

**触发条件**（满足任一即触发）：
1. **技术不可行**：意图文档中的业务约束或验收标准在当前技术架构下**不可能实现**（如"2 秒内完成"但现有系统基准测试显示最低 5 秒）
2. **根本性冲突**：意图文档中的要求与项目技术栈设计文档存在**不可调和的冲突**（如要求使用项目中明确禁止的技术）
3. **信息缺失导致无法决策**：意图文档中"留给规范阶段的技术决策"清单不完整，缺少关键技术决策项（如未定义并发策略、未定义数据一致性要求）
4. **业务定义自相矛盾**：意图文档中的业务规则存在逻辑矛盾，无法转化为一致的技术实现

**回退流程**：
1. **立即停止当前所有工作**，不得继续生成设计文档或落地规范
2. **向用户报告**：
   - 标记为 **"意图缺陷"**
   - 明确指出缺陷内容（引用意图文档的具体章节和原文）
   - 说明为什么这是技术不可行的（提供技术依据）
   - 说明 spec-writer **无权自行修改**意图文档
3. **给出回退路径**：
   > "请使用 module-intent-writer 回退到意图文档阶段，修正以下缺陷后重新冻结：\n"
   > "- [缺陷 1 描述]\n"
   > "- [缺陷 2 描述]\n"
   > "修正后重新冻结意图文档，再调用 module-spec-writer 进入规范阶段。"
4. **等待用户确认回退**，不自动执行任何操作

**禁止行为**：
- ❌ 禁止发现意图缺陷后自行修改或妥协（如把 2 秒改成 5 秒）
- ❌ 禁止绕过意图缺陷继续生成文档
- ❌ 禁止将意图缺陷隐藏在设计文档的注释中
- ❌ 禁止将技术不可行项推给用户说"你自己看着办"

### Step 4: 生成设计文档（瘦身版）

> **前置条件**：
> - SubAgent 报告已审查，无未解决业务矛盾（或矛盾已处理）
> - 轻量级确认已通过（用户确认或无异议）
> - 意图文档已冻结
> - 无未解决的意图缺陷（回退机制未触发或已处理）

先输出**设计文档（瘦身版）**，聚焦整体技术思路，不区分内外：

- **输出路径**：`docs/功能设计/[所属分组]/[模块编号]-[模块名称]/[模块编号]-[模块名称]-设计文档.md`
- **受众**：维护者、架构师
- **核心问题**："为什么这样实现？"

**内容来源**：以 SubAgent 的《技术决策完整报告》为核心依据，结合用户裁决结论。

> 若 SubAgent 报告与用户裁决存在冲突，**以用户裁决为准**，并在文档中标注冲突及最终选择理由。

**设计文档特有要求**：
- 聚焦技术实现思路、架构权衡、为什么选 A 不选 B
- 允许引用意图文档和总设计文档，但关键的技术决策依据必须显式写出
- 可包含技术备选方案的对比和选择理由
- **不包含**：项目定位、用户旅程、验收标准、业务约束（这些在意图文档中）
- **暂不包含精确的对外接口类型定义**（留到 Step 5 确定契约后补充）

详细模板见 `references/human-design-template.md`。输出时必须包含以下章节：

> 1.1 技术实现思路 → 1.2 已有设计兼容性分析 → 1.3 依赖关系概述（技术层面）→ 1.4 状态机设计（技术实现策略，如适用）→ 1.5 设计原则兑现清单（技术视角）→ 1.6 架构权衡与备选方案 → 1.7 注意事项与禁止行为（设计层面）→ 1.8 引用：配套意图文档

---

### Step 5: 对外接口定义与契约协调（先定边界）

> **目标**：先确定本模块与外部世界的边界——对外暴露什么接口、消费什么接口、与已有契约是否有冲突。
> **核心原则**：契约是"多方约定"，不是"单方声明"。任何冲突必须经用户裁决，SubAgent 不得自行决定。
> **关键产出**：`docs/contracts/{module_id}/*.json` + 落地规范对外章节（1.3/1.4/1.6/1.7）

#### 5.1 生成本模块对外接口类型草案

基于设计文档和 SubAgent 报告中的技术边界，生成落地规范的**对外章节初稿**：
- **1.3 输入定义**：本模块从外部接收的数据结构
- **1.4 输出定义**：本模块向外部返回的数据结构
- **1.6 接口契约**：公开函数的完整签名（docstring、参数、返回值、异常）
- **1.7 依赖与集成接口**：本模块调用的其他模块接口

**此时，对外接口类型仍写完整字段定义**（尚未进行契约协调，字段可能变更）。

#### 5.2 提取对外接口类型草案

从上述对外章节中提取所有对外类型，整理为临时 JSON 文件（不写入 `docs/contracts/`）：
```
.tmp/contract-draft/{module_id}/
├── WorldBuildInput.json
├── WorldBuildOutput.json
└── _draft-index.json
```

排除内部类型（私有函数参数、内部辅助模型、数据库映射模型）。

#### 5.3 调度 contract-harmonizer SubAgent

调用 `Agent` 工具，创建 SubAgent 执行 **contract-harmonizer**。

**关键参数**：
- `subagent_type`: "coder"
- `prompt`: |
    【你被 module-spec-writer 调度执行 contract-harmonizer SubAgent】
    任务：扫描已有契约文件，检查本模块的对外接口类型是否存在冲突或可复用项。
    本模块对外接口草案目录：{draft_dir}
    已有契约目录：docs/contracts/
    模块编号：{module_id}
    输出要求：《契约协调报告》（JSON 格式）
    绝对约束：
    - 禁止修改任何已有契约文件
    - 禁止自行裁决冲突——只发现和呈现

**SubAgent 职责**：参见 `agents/contract-harmonizer.md`

#### 5.4 主 Agent 处理协调报告

SubAgent 返回《契约协调报告》后，主 Agent 解析并处理：

**场景 A：发现冲突（`findings.conflicts` 非空）**
- 调用 `AskUserQuestion` 向用户呈现冲突详情
- 冲突裁决选项：
  1. 以已有契约为准 → 本模块修改类型定义以匹配已有契约
  2. 以本模块为准 → 标记已有契约为 `deprecated`，本模块新建契约
  3. 两者代表不同概念 → 本模块改名（避免同名冲突）
  4. 其他（用户自行描述）
- 用户裁决后，修正对外接口类型定义，重新提取契约草案，再次调度 SubAgent 验证

**场景 B：发现可复用类型（`findings.reusables` 非空）**
- 调用 `AskUserQuestion` 询问用户是否复用已有类型
- 用户确认复用 → 本模块删除重复定义，改为契约引用
- 用户拒绝复用 → 保留本模块定义，在契约文件中标注语义差异

**场景 C：无冲突、无可复用**
- 直接进入 5.5

#### 5.5 写入契约文件

协调完成后，将本模块的对外接口类型写入契约文件：

**目录结构**：
```
docs/contracts/
├── _index.json                      # 全局索引
├── {module_id}/
│   ├── _module-index.json           # 本模块契约清单
│   ├── {TypeName}.json              # 单个契约文件（JSON Schema）
│   └── ...
```

**契约文件格式**：必须符合 `references/schemas/contract.schema.json`
- `$schema`: 固定值
- `$id`: `docs/contracts/{module_id}/{TypeName}.json`
- `title`: 类型名称（与代码命名一致）
- `x-defined-by`: 本模块编号
- `x-consumers`: 消费方列表（初始为空，后续模块引用时更新）
- `x-maturity`: `draft`（仅本模块使用）或 `stable`（已有其他模块引用）
- `x-contract-type`: `input` / `output` / `shared-model` / `shared-enum` / `error-code` / `event`

**写入规则**：
- 本模块**独有**的对外类型 → 新建契约文件，`x-maturity: draft`
- 复用已有契约的类型 → 不新建，在 `_module-index.json` 中记录引用
- 与已有契约冲突、用户裁决以本模块为准 → 新建契约文件，更新已有契约为 `deprecated`

#### 5.6 更新落地规范对外章节为契约引用

将对外章节中的完整字段定义，替换为契约引用格式：

```markdown
### 1.3 输入定义（对外接口）【已锁定】

**WorldBuildInput**
- 【契约引用】`docs/contracts/M02/WorldBuildInput.json`
- 本模块作为该契约的定义方，消费方：暂无
- 契约版本: v1.0.0，锁定时间: 2026-05-05 21:00:00
```

> **【已锁定】标记**：对外接口章节一旦完成契约协调并写入 JSON，即视为锁定。后续对内设计（Step 6）不得修改对外接口的字段、类型或必填性。

#### 5.7 对外接口轻量级确认

向用户输出对外接口摘要：

```
本模块对外接口已确定，契约文件已写入 docs/contracts/{module_id}/。

对外接口摘要：
- 输入类型：[N] 个（列出名称）
- 输出类型：[N] 个（列出名称）
- 公开接口：[N] 个（列出函数名）
- 复用已有契约：[列表，或"无"]
- 新建契约：[列表]

如无异议，我将进入内部功能设计阶段（核心逻辑、状态机、异常处理）。
```

用户确认后进入 Step 6。

### Step 6: 对内功能设计（再填内容）

> **前置条件**：对外接口已锁定（Step 5 完成，契约文件已写入）
> **目标**：在已确定的对外边界内，设计模块的内部实现细节。
> **关键产出**：落地规范对内章节（1.5/1.8/1.9/1.10/1.11/1.12/1.13/1.14）

基于已锁定的对外接口，生成落地规范的**对内章节**：

| 章节 | 内容 | 约束来源 |
|:---|:---|:---|
| 1.1 技术栈绑定 | 必须使用/禁止使用的库和版本 | 项目技术栈设计文档 |
| 1.2 文件归属 | 源文件和测试文件路径 | 项目结构设计文档 |
| 1.5 核心逻辑步骤 | 原子操作步骤 | 意图文档 + 对外接口约束 |
| 1.8 状态机 | 状态转换表 | 意图文档 |
| 1.9 异常与边界条件 | 触发阈值、处理策略、重试参数 | 意图文档 + 对外接口约束 |
| 1.10 验收测试场景 | Given-When-Then + 完整 JSON | 意图文档验收标准 |
| 1.11 注意事项与禁止行为 | 编码层面约束 | 技术决策报告 |
| 1.12 文档详细度自检清单 | 自检项 | 规范要求 |
| 1.13 意图一致性声明 | 与意图文档一致性确认 | 意图文档 |
| 1.14 外部接口契约清单 | 所有契约文件路径列表 | Step 5 产出 |

**对内设计的边界约束**：
- 不得修改已锁定的对外接口类型（1.3/1.4/1.6）
- 内部类型可以完整定义，不受契约约束
- 核心逻辑步骤必须引用对外接口中定义的类型名，不得擅自改名

**落地规范对内章节特有要求**：
- 绝对禁止偷懒表述
- 每个类型字段必须包含完整约束和示例值（内部类型）
- 每个逻辑步骤必须包含：操作对象、具体操作、输入来源、输出去向、失败行为
- 每种异常必须包含：精确触发阈值/条件、逐步处理策略、精确重试参数
- 自检标准：如果文档中出现"这个很简单就不详细写了"等暗示性偷懒，必须重写

### Step 7: 输出最终文档

#### 7.1 合并落地规范

将 Step 5 生成的**对外章节**与 Step 6 生成的**对内章节**合并为最终落地规范：

```
落地规范 = 1.1 技术栈绑定 → 1.2 文件归属
         → 【对外部分，Step 5 锁定】
         → 1.3 输入定义（契约引用）【已锁定】
         → 1.4 输出定义（契约引用）【已锁定】
         → 1.6 接口契约【已锁定】
         → 1.7 依赖与集成接口【已锁定】
         → 【对内部分，Step 6 设计】
         → 1.5 核心逻辑步骤
         → 1.8 状态机（如适用）
         → 1.9 异常与边界条件
         → 1.10 验收测试场景
         → 1.11 注意事项与禁止行为
         → 1.12 文档详细度自检清单
         → 1.13 意图一致性声明
         → 1.14 外部接口契约清单
```

> 编号保持与模板一致，但落地规范内部用 `【已锁定】` / `【对内实现】` 标记区分生成阶段。

#### 7.2 输出文件清单

| 文件 | 路径 | 说明 |
|:-----|:-----|:-----|
| 设计文档（瘦身版） | `docs/功能设计/.../{编号}-{名称}-设计文档.md` | Step 4 生成，整体技术思路 |
| 落地规范 | `docs/功能设计/.../{编号}-{名称}-落地规范.md` | Step 5+6+7 合并，精确编码规格 |

- 不要合并多个功能点到同一份文档
- 设计文档不要逐字复制总设计的描述性段落——应当用自己的话解释技术实现意图和权衡
- 落地规范不要逐字复制总设计的描述性段落——每一句话要么是类型定义，要么是可测试的逻辑步骤，要么是明确约束
- 对歧义或未定义的部分，给出最佳推断。设计文档标注"（待确认，详见落地规范）"，落地规范标注"（待确认）"并附推断依据

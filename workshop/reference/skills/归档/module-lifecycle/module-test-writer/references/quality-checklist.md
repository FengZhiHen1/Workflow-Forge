# 质量检查清单

> 本清单是"自检动作记录"，不是"自我打分"。每个条目必须附带原始命令输出或客观证据，禁止仅凭主观判断打勾。
>
> 关键心态：你不是在"检查自己是否合格"，你是在**"给刚写完的验收测试做一次独立审阅"**。

## 常见问题模式与处理指南

### 1. G2 — "构造-断言" 的灰色地带

**场景 A：Pydantic 模型字段约束/默认值验证** ✅ 允许（有限范围）

仅当以下两个条件同时满足时，允许直接构造模型实例并断言：
1. 被测对象是 Pydantic model / dataclass 的**字段约束本身**（如默认值、min_length、pattern）
2. 断言验证的是**约束是否生效**，而非单纯字段存在

✅ 允许示例：
```python
# 验证 max_length=50 约束是否生效
with pytest.raises(ValidationError):
    WorldBuildInput(genre="x" * 51)

# 验证默认值是否正确应用（构造时省略字段，断言默认值）
def test_mode_default_is_incremental():
    model = CLIInput(chapter_id="ch-02")  # 省略 mode
    assert model.mode == "incremental"    # 验证默认值，而非构造时传入的值
```

❌ 禁止示例：
```python
# 构造时传入什么就断言什么——没有验证任何约束
output = CLIOutput(build_id="x", chapter_id="ch-02", ...)
assert output.build_id == "x"  # 与构造时传入的值一致，无约束验证价值
```

**场景 B：手动构造被测模型然后断言字段与构造值一致** ❌ 仍禁止

```python
# ❌ 禁止：典型的构造-断言
from ai_pipeline.models import PhaseIResult
def test_phase_i_success():
    result = PhaseIResult(status="success", error=None)
    assert result.status == "success"  # 与构造时传入的值一致，无验证价值
```

### 2. G3 — API 端点测试中的宽泛断言

**高频反模式**：用 `in` 包容多个互斥状态码或业务状态。

```python
# ❌ 禁止：3 个互斥状态码用 in 包容
def test_pause_with_reason(self, api_client):
    response = api_client.post("/pipeline/pause/...", json={"reason": "手动暂停"})
    assert response.status_code in (200, 404, 409)

# ✅ 正确：每个状态码分支独立测试
def test_pause_existing_build_returns_200(self, api_client): ...
def test_pause_nonexistent_build_returns_404(self, api_client): ...
def test_pause_already_paused_returns_409(self, api_client): ...
```

### 3. G8 — 恒真式欺骗的新变种

Agent 可能在修复 G4（纯存在性断言）时，用 `or True` 欺骗扫描器：

```python
# ❌ 典型欺骗：修复 G4 时引入 G8
assert len(nodes) >= 2 or True  # 看起来变强了，实际还是永真
assert hasattr(compiled, "get_graph") or True  # 同上

# ✅ 正确修复：去掉 or True，写可证伪的断言
assert len(nodes) >= 2
assert hasattr(compiled, "get_graph")
```

**检测建议**：运行扫描器后，不仅要看 G4 是否降为 0，还要确认 G8 也是 0。

### 4. G9 — 防御性跳过的"合法"伪装

Agent 可能把 `try-except-pass` 改成 `if condition: return`，认为这样更"干净"：

```python
# ❌ G9 命中：防御性跳过
if api_client is None:
    return

# ❌ G1 命中：异常吞咽（同样有害）
try:
    ...
except ImportError:
    pass

# ✅ 正确做法：测试就应该在依赖缺失时失败，发出信号
# 如果 API 端点尚未实现，不写这个测试，或写 stub 让它调用时抛出明确异常
```

### 5. 标准库测试的边界判断

直接测试标准库原语（如 `asyncio.Semaphore`、`asyncio.gather`）如果没有调用被测模块，按字面标准属于 G2+G5。

但若设计文档明确声明了并发约束（如"使用 Semaphore(3) 限制并发"），测试应**优先通过被测模块的包装函数验证**。只有在被测模块未暴露包装函数时，才允许直接测试原语，且必须在注释中引用设计文档的对应章节。

### 6. 趋绿扫描器已知限制

| 场景 | 当前行为 | 处理方式 |
|:---|:---|:---|
| `from module import func; func()` | 已正确识别 | 无需人工确认 |
| `self._helper()` 内部调用被测函数 | 已穿透一级 | 无需人工确认 |
| `api_client.post()` 等 HTTP 客户端 | 已识别 | 无需人工确认 |
| 防御性 `try-except-pass` | 已降级为毒性 1 | **需人工确认** |
| 控制流异常（`structlog.DropEvent`） | 已降级为毒性 1 | **需人工确认** |
| `or True` 在复杂表达式中 | 已检测 | 无需人工确认 |
| `if condition: return` 在嵌套 if 中 | 已递归检测 | 无需人工确认 |

## 实现差异处理指南

当读取实现代码后发现与落地规范存在差异时：

| 差异类型 | 示例 | 处理方式 |
|:---|:---|:---|
| 轻微差异（字段名不同，语义一致） | 规范用 `user_id`，实现用 `uid` | 按实现编写测试，在报告中标注 |
| 重大差异（缺少契约要求的异常） | 规范要求空字符串抛 ValidationError，实现未校验 | 记录为"实现缺陷"，测试仍按契约编写（应失败），向用户报告 |
| 实现有而规范无的功能 | 实现额外支持了缓存 | 记录为"实现扩展"，补充测试覆盖，向用户报告 |
| 规范有而实现无的功能 | 规范要求重试 3 次，实现未实现 | 记录为"实现缺陷"，测试按契约编写（应失败），向用户报告 |

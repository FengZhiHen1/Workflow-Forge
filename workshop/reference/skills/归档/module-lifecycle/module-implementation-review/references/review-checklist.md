# 模块级审查清单

按此清单逐项审查每个模块，确保不遗漏关键检查点。

---

## 1. 设计文档定位

- [ ] 模块编号已明确（如 M01、M02）
- [ ] 找到对应的两份设计文档：`[编号]-[名称]-设计文档.md` 和 `[编号]-[名称]-落地规范.md`（或旧版单文件）
- [ ] 从落地规范提取了交付物清单、接口契约（输入、输出、异常、边界条件）
- [ ] 从设计文档提取了联动关系（依赖谁、被谁依赖、数据流）
- [ ] 若仅找到其中一份，记录为"⚠️ 设计文档不完整"

> 如果找不到任何设计文档，记录为"⚠️ 缺失设计文档"，跳过 2-4 步，仅检查代码文件是否存在。如果是旧版单文件文档，所有信息从同一文件提取。

---

## 2. 交付物完整性检查

对每个预期文件：

- [ ] **文件存在**：磁盘上存在该路径
- [ ] **文件非空**：大小 > 0 字节
- [ ] **语法有效**：通过语言级语法检查（如 py_compile、tsc）
- [ ] **符号存在**：核心类/函数/接口已在文件中定义
- [ ] **非占位实现**：不是仅包含 `pass`、`TODO`、`FIXME` 的空壳
- [ ] **导入可解析**：没有 `ModuleNotFoundError` 等导入错误

**占位符判定标准**：
- 函数体只有 `pass` / `...` / `raise NotImplementedError`
- 类方法全部未实现
- 文件仅有注释无实际代码
- 存在 `TODO` / `FIXME` / `XXX` 标记且占主导

---

## 3. 接口契约符合性

- [ ] **函数/方法签名匹配**：参数名、参数数量、参数顺序与设计一致
- [ ] **类型注解存在**（如设计文档要求）
- [ ] **返回值处理**：有明确的 return 语句，返回类型与设计一致
- [ ] **异常处理**：设计文档要求的异常/错误码已实现
- [ ] **边界条件**：设计文档中的边界约束在代码中有校验逻辑

> 允许合理的工程化调整（如增加可选参数、使用 kwargs），但核心契约必须保持一致。

---

## 4. 核心逻辑正确性

- [ ] **主流程可运行**：模块的核心功能流程能够执行（可用 mock 数据测试）
- [ ] **分支覆盖**：设计文档中提到的条件分支在代码中有对应实现
- [ ] **状态转换**：如涉及状态机，状态转换逻辑正确
- [ ] **算法/公式**：如涉及算法，公式实现与设计文档一致
- [ ] **配置读取**：配置项从正确位置读取（环境变量、配置文件等）

---

## 5. 测试检查

- [ ] **测试文件存在**：有对应的 `test_*.py` / `*.test.ts` 等
- [ ] **测试可收集**：`pytest --collect-only` 或对应工具的收集命令无报错
- [ ] **核心用例覆盖**：至少覆盖了设计文档中的"正常流程"和"主要异常流程"
- [ ] **断言有效**：测试中有实际断言，不是空测试
- [ ] **测试通过**：运行测试，通过率达到可接受水平

---

## 6. 文档与注释

- [ ] **模块级注释**：文件头部有功能说明（如设计文档要求）
- [ ] **接口文档**：公开 API 有 docstring / JSDoc / 注释说明
- [ ] **复杂逻辑注释**：设计文档标记为"关键/复杂"的逻辑有注释

---

## 7. 严重级别定义

| 级别 | 图标 | 定义 | 示例 |
|------|------|------|------|
| 严重 | 🔴 | 模块核心功能无法运行或联动中断 | 文件缺失、主函数未实现、接口签名不匹配导致调用失败 |
| 中等 | 🟡 | 功能可用但存在质量/稳定性风险 | 测试缺失、边界条件未处理、异常处理不完整 |
| 轻微 | 🟢 | 代码可运行，属于优化/债务项 | 命名不规范、缺少类型注解、注释不足 |

---

*使用此清单时，将每个检查项的结果填入审查报告的对应模块章节。*

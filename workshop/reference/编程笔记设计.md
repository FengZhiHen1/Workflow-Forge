## 编程语言原子笔记体系：设计思想总纲

### 一、核心哲学：从"命题驱动"到"行为驱动"

数学规范以**命题**为中心（定义是什么、定理证明什么），因为数学的正确性由逻辑保证。编程语言以**行为**为中心（语法怎么写、运行期发生什么、工具怎么处理），因为编程的正确性由**编译器/解释器/运行时**共同决定。

因此，本体系的设计哲学是：

> **记录的不是"代码长什么样"，而是"代码在特定环境下会表现出什么行为，以及为什么"。**

这意味着：
- 语法笔记必须绑定语义上下文，不能孤立记录文法
- 语义笔记必须绑定具体环境（语言版本、编译器、平台），不能空谈"标准说"
- 陷阱不是反例，而是**行为边界的必要注释**，必须嵌入到相关知识点中

---

### 二、原子类型体系：七类一辅，语义优先于形式

我们保留了数学规范"原子化 + 语义分类"的骨架，但将类型重构为**行为驱动**的七类：

| 类型 | 核心问题 | 与数学的对应关系 |
|------|----------|----------------|
| **语法** | 怎样写是合法的？ | ≈ 定义（但记录的是规则而非概念构造） |
| **语义** | 运行期实际发生什么？ | ≈ 定理/性质（但记录的是行为保证而非逻辑命题） |
| **API** | 接口契约与边界是什么？ | 无直接对应（编程特有） |
| **惯用法** | 在特定场景下应该怎样写？ | ≈ 方法（但强调代码模式而非解题步骤） |
| **工具链** | 编译器/解释器/包管理器如何处理代码？ | 无直接对应（编程特有） |
| **原则** | 语言为什么这样设计？ | ≈ 公理（但可讨论、可演变） |
| **对比** | 跨语言/跨版本的差异是什么？ | 无直接对应（大模块独立，小差异融入子章节） |

**关键约束**：
- **API 不盲目原子化**：只有"大体量"（完整生命周期模型，如 `std::vector`）和"易错体量"（行为反直觉，如 `remove` + `erase` 惯用法）才建独立原子笔记；普通 API 在惯用法或项目笔记中以代码块引用。
- **对比受限独立**：一般差异作为语法/语义/API 笔记的 `## 版本演进` 或 `## 跨语言对比` 子章节；仅在"大模块级"跨语言/跨版本专题时才独立成篇。

---

### 三、语法与语义的关系：主从融合，复杂度分级

我们不采用"一刀切"的分离或合并，而是根据**认知负荷**动态决定：

> **简单绑定 → 融合笔记；复杂交互 → 分离笔记。**

- **融合（约 70%）**：语法笔记为主体，语义作为 `## 运行期语义` 子章节。适用于语义可在 3 句话内说清、且仅绑定单一语法点的知识（如 Python 列表推导式的作用域隔离）。
- **分离（约 30%）**：语义独立成篇，通过双链关联多个语法笔记。适用于语义涉及多语法点交互（如 C++ 完美转发 = 模板推导 + 引用折叠 + `std::move`），或在多处被引用的通用行为保证（如 Python "赋值即引用"）。

**判定准则**：分离不是为了"原子化而原子化"，而是为了**降低工作记忆负担**——当一页放不下、或需要跨语法点引用时，才拆。

---

### 四、陷阱的融入策略：作为知识点的"阴暗面注释"

陷阱不独立成类，而是作为**各类型笔记的固定警示模块**：

| 原子类型 | 陷阱位置 | 形式 |
|----------|----------|------|
| 语法/语义/API/惯用法 | `## 理解与细节` | `> [!warning]` |
| 工具链 | `## 理解与细节` | `> [!warning]` |
| 原则 | `## 反模式` | `> [!warning]` |

**铁律**：`> [!warning]` 中的代码**禁止折叠**，因为陷阱的价值在于"一眼看到错误"。

这体现了编程学习的核心认知规律：**从错误中学习的效率远高于正向学习**。陷阱不是附赠内容，而是知识点的必要组成部分。

---

### 五、代码规范：环境绑定与分层展示

代码在编程笔记中的角色远比数学公式复杂——它既是**知识载体**，又是**可执行对象**。因此我们设计了分层容器策略：

| 场景 | 容器 | 折叠策略 | 验证要求 |
|------|------|----------|----------|
| 短片段/核心语法 | fenced code block | 不折叠 | 可选 |
| 完整可运行示例 | `> [!example]-` | **折叠** | 建议标注 |
| 错误/UB/陷阱复现代码 | `> [!warning]` | **不折叠** | **必须标注** |

**环境标注**（`# env: Python 3.11.4 / CPython / macOS 14`）不是过度工程，而是**时间戳**——编程知识高度依赖版本，没有环境信息的代码片段在两年后可能变成误导。

**注释语言**：中文为主，正文承担详细解释。这是**个人学习笔记**，不是开源项目，优先保证理解速度而非工程规范。

### 六、YAML 设计：显式、分层、可查询

frontmatter 是笔记的**数据骨架**，设计原则是**"查询时不依赖路径，维护时不依赖记忆"**。

关键决策：
- **`language` 显式声明**：不通过文件夹路径隐含，因为编程笔记的跨语言引用极其常见（如 C++ RAII 对比 Python `with`）。
- **`standard` 分层要求**：语法/语义/API/工具链 必须标注标准版本；原则可选。主文件聚焦**最新标准**，历史差异在正文 `## 版本演进` 中展开。
- **`library: stdlib`**：标准库显式写 `stdlib`，与第三方库（`requests`、`Flask`）统一字段，避免查询时的歧义。
- **`library` 字段约束**：仅在 `type: API` 中使用。其他类型若涉及第三方库示例，在正文标注，不写入 frontmatter，防止元数据污染。
- **`platform` 可选**：仅在工具链或平台特定笔记中使用，普通笔记省略以保持精简。
- **`status` 不引入"已废弃"**：特性废弃是语义属性，不是笔记状态。废弃特性笔记保持 `已整理`，在正文中用 `> [!warning]` 标注废弃信息，保留历史参考价值。
- **`tags` 自由 + 白名单**：领域标签（如 `内存管理`、`并发`）建议优先使用白名单，但不强制，避免领域扩展时卡住。

### 七、与数学规范的继承与差异

| 维度 | 数学规范 | 编程规范 |
|------|----------|----------|
| **分类逻辑** | 逻辑命题形态（定义/定理/引理） | 行为维度（语法/语义/工具链） |
| **时效性** | 无版本概念 | 强版本绑定（`standard`、`library`、`platform`） |
| **反例/陷阱** | 独立类型 `反例`，辅助证伪 | 融入各类型 `> [!warning]`，核心学习路径 |
| **实践验证** | 逻辑证明 | 环境标注 + 可运行代码 |
| **代码展示** | LaTeX 公式 | 分层容器 + 环境标注 |
| **双链逻辑** | 线性推导链 | 网状层级（语法 → 语义 → API → 惯用法 → 项目） |

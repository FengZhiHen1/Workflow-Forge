# 工作流设计思想

---

## 一、程序做程序的活，AI 做 AI 的活

工作流调度中，读 DAG、判依赖、推状态流转——这些都是机械规则，输入确定则输出确定，不需要"判断"，只需要"计算"。这些事情不应该放在 AI prompt 里。

系统由三个互不重叠的角色构成：

| 角色 | 本质 |
|------|------|
| **主 Agent** | 智能决策者——理解意图、匹配工作流、呈现确认、把握全局进度 |
| **wfctl** | 机械调度器——读 YAML、判就绪、推流转、返回结构化指令 |
| **SubAgent** | 执行者——在隔离 worktree 中干活，通过 Message 上报 |

---

## 二、主 Agent 是指挥者

主 Agent 即承载本系统的 Agent 应用（如 Claude Code、Kimi Code）。它不是系统中额外创建的一个子智能体，而是宿主应用本身。

它是整个工作流体系的指挥中心，持有项目级全局视野——知道哪些模块已完成、哪些正阻塞、哪些可以并行启动。它不是被动等待用户逐个指令，而是主动判断"现在该推进什么"。遇到新需求时自主匹配工作流、创建实例、纳入调度。

wfctl 是它手中的工具，通过命令行调用，不在系统中作为对等的独立实体存在。

---

## 三、wfctl 是机械调度程序

wfctl 是纯 Python 程序，不含 AI。它做的事情是确定性的——输入一致，输出一致。主 Agent 每次循环调用它，获得一个明确的指令：该启动哪个 stage、该向用户呈现什么确认、还是该静默等待。主 Agent 依指令行动。

### 循环触发

主 Agent 在以下时机驱动 wfctl：

| 触发源 | 行为 |
|--------|------|
| 用户发出指令 | 主 Agent 解析意图，必要时 wfctl resolve → create → 进入调度循环 |
| SubAgent 完成通知 | 主 Agent 收到系统通知，调用 wfctl 上报结果并获取下一步指令 |
| 用户回复确认 | 主 Agent 将结果传回 wfctl，继续推进 |

wfctl 本身是无状态、无等待的——每次调用即读盘、计算、返回。主 Agent 是循环的驱动者。

wfctl 不接触用户，不启动 SubAgent，不做语义判断。

---

## 四、最大化推进，只在语义阻塞点暂停

实例化不需要确认。并发不需要用户指令。阶段间流转不需要人点"继续"。阻塞只应发生在真正的语义决策点——方案选型、方向分歧、质量存疑。其余时间全速推进。

SubAgent 通过 Message 发出确认请求（status=AWAITING_CONFIRM）后，主 Agent 收口呈现给用户，绝不绕过用户自行决策。

Skill 可以自然使用 AskUserQuestion——框架在 SubAgent 启动时先于 SKILL.md 注入替换规则，SubAgent 自觉将 AskUserQuestion 转为 AWAITING_CONFIRM 消息。用户确认后，答案注回**同一个** SubAgent 实例，实例从暂停点继续执行。

### 两级合并

| 方向 | 触发方 | 默认行为 |
|------|-------|---------|
| Stage → 实例 worktree | wfctl（自动） | 无阻塞，直接合并 |
| 实例 worktree → 主仓库 | 主 Agent（确认点） | 需要用户确认，可配置为自动 |

流程内部全速推进。**流程最终是否写入主仓库，由用户决定。**

---

## 五、两级 worktree 隔离

本系统自行管理 worktree 生命周期，不依赖特定平台的隔离机制，确保跨平台可移植。

### 实例级 worktree

工作流实例创建时，为其分配一个实例 worktree。该实例的所有 stage 默认共享此 worktree，SubAgent 在其中顺序执行，天然看到上游产出。

### 并发时按 stage 拆分

仅运行一个 stage 时，直接使用实例 worktree，不额外拆分。

同时启动多个 stage 时，为每个 stage 分配独立的 stage 级 worktree。Stage 完成后，wfctl 尝试将其 worktree 变更合并回实例 worktree：无冲突则自动合并，有冲突则标记为待处理并上报主 Agent，不静默覆盖。并发解除后，后续 stage 回到实例 worktree 中执行。

### 回退

回退到某 stage = 从该 stage 的锚点重建实例 worktree，重新出发。stage 级 worktree 的临时分支不产生持久化的分支痕迹。

---

## 六、git 锚点：跨阶段追溯

每个 stage 完成后，在实例 worktree 内打一个 lightweight git tag（如 `wf-{instance_id}-{stage_id}`）。这些 tag 仅存在于实例 worktree 中，不推送远程，不进入主仓库历史。

锚点的作用不是对外发布，而是实例内部的回溯。下游 stage 发现上游引入的问题时，可定位到对应锚点、重建实例 worktree，从该节点重新出发。

实例 worktree 合并回主仓库时，若主仓库在此期间有新提交，由主 Agent 介入辅助用户解决冲突，不自动覆盖。合并完成后打最终锚点，标记一次完整的工作流写入。

---

## 七、Message 是唯一通信协议

SubAgent 与主 Agent 之间仅通过 Message 通信。SubAgent 上报状态、产出列表、确认请求。Message 是隔离体系中唯一保留的通信通道——SubAgent 通过 wfctl 的写入功能将 Message 落盘到原仓库的 `.agent/messages/`，不经过实例 worktree 的文件隔离。源代码不可触，通信通道可用。

你从不直接与 SubAgent 对话。所有确认由主 Agent 统一收口。

---

## 八、状态机极简

Instance 四种状态：`ACTIVE` / `PAUSED` / `COMPLETED` / `FAILED`。

Stage 五种状态：

```
PENDING → RUNNING → DONE
             ↓
        AWAITING_CONFIRM → RUNNING（用户确认后恢复）
             ↓
           ERROR → PENDING（重试）
           PAUSED → 实例级暂停，所有 RUNNING stage 回退到 PENDING
```

`AWAITING_CONFIRM` 是 wfctl 调度逻辑中的阻塞状态——stage 未完成，不重试，不解锁下游。wfctl 不依赖外部上下文判断"这个 stage 该不该停"，状态本身就说了。

历史记录（SKIPPED、SUPERSEDED 等）写入独立日志，不参与流转计算。

---

## 九、失败路径与成功路径同等重要

每个 stage 必须定义失败行为——重试、跳过、或终止实例。wfctl 在阶段级处理超时与清理残留 worktree，在实例级持久化状态以便崩溃后从磁盘恢复。

可靠的工作流框架不仅取决于正常路径，同样取决于异常路径。

### 存活检测的物理约束

SubAgent 是 LLM 进程，没有独立定时器线程——不存在 Temporal 式的进程级心跳。存活检测全部由宿主平台承担：

| 信号 | 检测方 | 机制 |
|------|--------|------|
| 进程正常退出 | 宿主平台 | 平台通知主 Agent |
| 进程崩溃（OOM、异常终止） | 宿主平台 | 平台通知主 Agent |
| 进程卡死（API 挂起、网络中断） | 宿主平台 | `timeout_seconds` 到期，平台终止 SubAgent 并通知主 Agent。主 Agent 收到通知后调用 `next`，wfctl 将 stage 置为 ERROR 并走 retry 分支 |

主 Agent 始终是**响应者**——它调用后台 SubAgent 后不阻塞轮询，只在收到平台通知时驱动 wfctl。不存在 LLM 进程级的主动心跳。不引入提示词注入式的"定期上报 RUNNING"——它在工具调用/API 挂起期间无法执行，不比平台 timeout 提供更多信息，反而让 Skill 沾染工作流协议。

---

## 十、权限靠隔离，不靠自觉

防线分四层：

| 层 | 何时生效 | 做什么 |
|----|---------|------|
| worktree 隔离 | SubAgent 运行中 | 物理屏障——SubAgent 不知 `project_root`，世界局限于自身 worktree |
| wfctl 事后校验 | SubAgent 上报完成时 | `git status --porcelain` 获取变更，比对保护区，违规 → ERROR + deviation + 锚点回退 |
| git 锚点可逆 | 任何时刻 | 违规修改可以从锚点回退，reflog 保留 30 天 |
| prompt 禁令 | SubAgent 启动时 | SubAgent 自行读取 `common.md` 中的硬禁令——兜底，不依赖它生效 |

不依赖 AI 自觉，依赖架构本身的隔离性和可校验性。

详见 `权限与校验体系规范`。

---

## 十一、上下文压缩：全局视野不靠全量加载

主 Agent 持有全局视野，但不能把所有 stage 的原始输出全塞进上下文。每个 stage 完成后，SubAgent 在自己的 Message 中提供结构化摘要——产出列表、关键结论、待处理问题。wfctl 提取这些摘要字段，组装为结构化的进度信息返回给主 Agent。主 Agent 只持有这些摘要。需要详情时，从日志和 Message 文件中定向查询，用完即弃。

主 Agent 脑中的不是"所有发生过的事"，而是"当前大局 + 下一步做什么"。这确保长工作流不会因上下文膨胀而失忆。

---

## 十二、开发者可观测性

工作流不是黑盒。开发者有权在任何时候看到：

- 项目整体进度：哪些实例在跑、哪些 stage 完成、哪些在阻塞
- 当前 SubAgent 在做什么：不只是"RUNNING"，而是可被查询的执行状态
- 出问题时发生了什么：异常状态附带诊断信息——哪个 worktree、相关 Message 路径、建议操作

wfctl 提供状态视图，主 Agent 据此向开发者呈现。开发者不需要翻 JSON 文件来排查问题。

# Workflow Designer 设计原则

> **前置要求**：已读取 `workshop/specs/工作流思想.md`。本文件是对其的继承与扩展——不重复哲学论述，只补充操作层内容。
> 用途：指导 workflow-designer 的所有设计决策。三轨制的差异体现在这些原则的应用深度。

---

## 原则分层

```
┌─────────────────────────────────────────────────────────────┐
│  不可妥协原则（所有轨道必须100%遵守）                          │
│  ─────────────────────────────────────                      │
│  失败路径完整 / 无审批不修改 / 双重视角 / 可观测性             │
├─────────────────────────────────────────────────────────────┤
│  核心原则（所有轨道应用，深度可调）                            │
│  ─────────────────────────────────────                      │
│  程序AI分工 / 实时留档 / 不挑输入                             │
├─────────────────────────────────────────────────────────────┤
│  扩展原则（深度设计全面应用，快速通道可裁剪）                   │
│  ─────────────────────────────────────                      │
│  语义阻塞点 / 上下文压缩 / 讨论执行 / 共享资源 / 隔离分层        │
└─────────────────────────────────────────────────────────────┘
```

## 不可妥协原则

### P1: 失败路径与成功路径同等重要

**来源**：`workshop/specs/工作流思想.md` —— "可靠的工作流框架不仅取决于正常路径，同样取决于异常路径。"

**定义**：每个 Stage 的产出必须包含完整的异常路径定义。`success` edge 和 `failure` / `rejected` / `loop_exceeded` edge 同等重要，不可因"简单"或"默认"而省略。

**正例**：
```yaml
edges:
  - from: s01
    to: s02
    condition: success + choice
    choice: "通过"
  - from: s01
    to: s99-workflow-end
    condition: success + choice
    choice: "放弃"
  - from: s01
    to: s01
    condition: success + choice
    choice: "继续完善"
    max_loop: 5
  - from: s01
    to: s99-workflow-end
    condition: loop_exceeded
```

**反例**：只写了 `confirmed` 出边，没有 `rejected` 和 `loop_exceeded`。

**轨道差异**：所有轨道100%遵守。快速通道通过 designer-fast 内置异常路径模板自动补全。

---

### P2: 无审批不修改

**来源**：`SKILL.md` —— "无审批不修改：除非用户明确批准，不擅自改动任何文件。"

**定义**：任何写入 `artifacts/` 的操作前必须有用户确认。决策文档的填写可以实时进行，但转正（移动/覆盖文件）必须是强制门控。

**正例**：
> 转正预览：
> - 目标路径：`artifacts/workflows/my-wf@1.0.0/`
> - 产物清单：WORKFLOW.yaml + WORKFLOW.md + 2个skills
> - [确认转正] / [再检查一下] / [取消]

**反例**：SubAgent 生成文件后，主 Agent 自动复制到 `artifacts/` 而不询问用户。

**轨道差异**：所有轨道100%遵守。门控数量不因快速通道而减少（仍为：方向确认 + Phase 1确认 + 转正确认），但门控前的讨论轮次可以减少。

---

### P3: 双重视角

**来源**：`SKILL.md` —— "产出物按生产车间规范落盘，产出物内容按消费者项目规范定位。"

**定义**：SKILL.md 和 WORKFLOW.md 中引用的所有路径必须使用消费者项目规范（`.claude/`、`.agent/`），绝不能出现生产车间路径（`artifacts/`、`workshop/`）。落盘路径用生产车间规范。

**关键补充**：Skill 引用工作流级共享资源时，必须使用**相对于项目根目录的路径**（如 `.claude/workflows/<id>/references/xxx.md`），禁止使用相对路径（如 `../references/xxx.md`）。Skill 不知道自己在 `.claude/skills/<id>/` 下，相对路径会因目录深度不同而失效。

**正例**：
- SKILL.md 中写 "读取 `.claude/contracts/common.md`"
- SKILL.md 中写 "读取 `.claude/workflows/my-wf/references/directory-convention.md`"

**反例**：
- SKILL.md 中写 "读取 `artifacts/contracts/common.md`"
- SKILL.md 中写 "读取 `../references/directory-convention.md`"

**轨道差异**：所有轨道100%遵守。快速通道可通过脚本自动替换路径，不以此展开讨论。

---

### P4: 可观测性

**来源**：`workshop/specs/工作流思想.md` —— "开发者有权在任何时候看到：项目整体进度、当前 SubAgent 在做什么、出问题时发生了什么。"

**定义**：设计工作流时，每个 Stage 的产出必须是可验证的。用户在使用 workflow-designer 时，每一步都必须清楚"现在到哪了、还要多久、下一步是什么"。

**正例**：
> Phase 1 完成。已确定 5 个 Stage，2 个确认点。即将进入 Phase 2，预计需要生成 3 个 Skill。

**反例**：
> 好的，我在设计。等一会儿。（用户不知道进度）

**轨道差异**：所有轨道100%遵守。快速通道用一句话播报，深度设计用结构化摘要 + dependency-graph 可视化。

## 核心原则

### P5: 程序做程序的活，AI 做 AI 的活

**来源**：`workshop/specs/工作流思想.md` —— "读 DAG、判依赖、推状态流转——这些都是机械规则，不需要'判断'，只需要'计算'。"

**定义**：规则明确的任务交给脚本（路径替换、格式校验、依赖图构建），语义判断交给 AI（Stage 拆分合理性、确认点时机、用户体验）。

**应用**：
- 脚本化：`validate_workflow.py`、`evaluate_workflow_design.py`、路径自动替换
- AI判断：Stage 职责定义、确认点设计、业务逻辑保留

**轨道差异**：快速通道更多依赖人工判断（减少脚本介入），深度设计强化脚本与 AI 的分工（依赖图脚本生成 + reviewer AI 评审）。

---

### P6: 实时留档

**来源**：`SKILL.md` —— "讨论中随时将已确定的决策写入决策文档，不等到最后一口气。"

**定义**：每个设计决策在用户确认后立即写入对应决策文档。决策文档是设计的"活档案"，而非事后补写的总结。

**应用**：
- Phase 1 决策文档：每讨论完一个维度立即填入
- Phase 2 决策文档：每 Skill 的讨论结论实时写入

**轨道差异**：所有轨道都维护决策文档。快速通道用简化模板，深度设计用完整模板。

---

### P7: 设计工作流，不挑输入

**来源**：`SKILL.md` —— "旧 Skill 能改造，已有工作流能重构，空白需求能新建。"

**定义**：workflow-designer 不应拒绝任何形态的输入。无论用户提供的是旧 Skill、已有工作流、还是一句话需求，都能进入设计流程。

**应用**：
- 旧 Skill → 提取逻辑步骤 → 映射为 Stage
- 已有工作流 → 读取 WORKFLOW.yaml → 分析改进空间
- 从零开始 → 引导用户澄清需求 → 从目标反推 Stage

**轨道差异**：所有轨道支持全输入类型。轨道选择依据"原则需求"而非"输入类型"。

## 扩展原则

### P8: 最大化推进，只在语义阻塞点暂停

**来源**：`workshop/specs/工作流思想.md` —— "阻塞只应发生在真正的语义决策点——方案选型、方向分歧、质量存疑。"

**定义**：工作流设计中，格式确认、路径选择、默认参数等不需要用户阻塞。只有"这个 Stage 该不该拆""确认点时机对不对"等语义决策才需要用户参与。

**应用**：
- 快速通道：语义阻塞点只留 2 个（方向确认 + 转正确认）
- 标准设计：5 维度每个都是潜在阻塞点
- 深度设计：7 维度 + 设计评审，但用户可标记"跳过"

**轨道差异**：快速通道裁剪阻塞点数量，深度设计扩展阻塞点类型但允许用户跳过。

---

### P9: 上下文压缩

**来源**：`workshop/specs/工作流思想.md` —— "全局视野不靠全量加载。主 Agent 只持有摘要，需要详情时定向查询。"

**定义**：设计过程中，不需要把旧 Skill 的全文或已有工作流的所有细节都加载到上下文中。提取结构化摘要，按需深入。

**应用**：
- analyzer 产出结构化 YAML 报告，不复制原文
- skill-writer 消费决策文档中的"需求规格"，不读取完整的 Phase 1 讨论记录

**轨道差异**：快速通道只加载 SKILL.md 原文（主 Agent 内联提取），深度设计通过 analyzer 产出结构化摘要。

---

### P10: 讨论串行、执行并行

**来源**：`SKILL.md` —— "讨论以自然对话进行，追求设计质量；执行调度 SubAgent，一个只做一件事。"

**定义**：设计决策阶段（讨论）允许多轮对话，不追求速度；执行阶段（SubAgent 调度）应最大化并行。

**应用**：
- Phase 1：主 Agent 与用户串行讨论
- Phase 2：skill-writer 尽可能并行调度

**轨道差异**：快速通道串行生成（简单场景并行收益低），深度设计按依赖层级并行。

---

### P11: 共享资源意识

**来源**：`SKILL.md` —— "工作流不是一组孤立 Stage 的串联——应当主动识别能被多个 Skill 复用的资源。"

**定义**：设计工作流前，先建立"提取共享资源"的意识。被 2 个及以上 Skill 使用的资源应提升到工作流级。

**应用**：
- `directory-convention.md`：定义产物目录结构
- `agent-protocol.md`：定义 Agent 行为规范
- `scripts/`：共享工具脚本

**轨道差异**：快速通道识别后可跳过（用户说"不需要"就不建），深度设计强制"识别 → 论证 → 建立 → 校验引用完整性"。

---

### P12: 隔离分层

**来源**：`workshop/specs/工作流思想.md` —— "权限靠隔离，不靠自觉。worktree 隔离 + 事后校验 + git 锚点可逆。"

**定义**：设计工作流时，Stage 之间的隔离性应被显式考虑。每个 Stage 的 SubAgent 应只感知自己的输入和输出，不感知全局工作流结构。

**应用**：
- v3 规范下 Skill 不感知 `confirmation_point`（由编排器处理）
- Skill 不写入 `AskUserQuestion` / SubAgent 调度（由工作流层处理）
- 共享资源通过 references/ 引用，不重复内联

**轨道差异**：所有轨道遵守 v3 规范。深度设计增加"集成校验"，验证 Skill 间接口一致性。

# 原则类原子笔记写作规范 (Principle Note Specification)

## 适用分类

YAML `type: 原则`，Callout `> [!abstract] 原则：[名称]`。

> 原则笔记回答"语言/API 为什么这样设计？"记录深层设计动机、编程范式约束。与数学公理不同，原则**可讨论、可演变**。

# {学术描述性名称}

> [!abstract] 原则：{名称}
> 原则的一句话概括：什么设计目标 + 核心约束 + 付出的代价。

- 历史背景：在什么场景下这个原则变得重要？
- 如果不遵循这个原则会怎样？

## 各节写作要求

### `> [!abstract] 原则：[名称]`
- **内容**：一句话归纳——设计目标 + 核心约束 + 代价
- **示例**："Rust 所有权系统的设计原则：在编译期保证内存安全，无需垃圾回收器。核心约束：每个值有且只有一个所有者。代价：学习曲线陡峭，某些模式需要额外编码（如共享状态需用 `Rc`/`Arc`）。"

### `## 设计动机`
- **问题**：该原则试图解决什么痛点？
- **历史**：在什么背景下诞生？（如 C 的内存泄漏和悬垂指针催生了 Rust 的所有权）
- **后果**：不遵循会导致什么问题？

### `## 核心约束`
- **格式**：有序列表 `1. `，按重要性排序
- **内容**：该原则对代码/架构施加的强制性约束
- **要求**：每条约束应可转化为代码审查清单中的具体检查项

### `> [!example]- 遵循示例`
- **折叠**：使用 `-` 后缀折叠
- **内容**：展示遵循该原则的良好代码
- **对比价值**：与反模式形成对照

### `> [!warning] 反模式`
- **铁律**：代码**禁止折叠**
- **结构**：
  - 反模式名称
  - 为什么违反原则？
  - 错误代码示例（带 `// ❌` 注释）
  - 正确做法（带 `// ✅` 注释）

### `## 权衡与讨论`
- **适用范围**：该原则不是绝对的——在什么场景下特别重要？什么场景下可妥协？
- **原则冲突**：与其他设计原则的冲突（如 DRY vs YAGNI）
- **跨语言视角**：不同语言如何实现类似目标？（如 C++ RAII、Python `with`、Go defer）

## 原则 vs 语义/语法的区分

| 维度 | 原则类 | 语义类 | 语法类 |
|------|--------|--------|--------|
| 标题 | "原则：XXX" | "语义：XXX" | "语法：XXX" |
| 核心问题 | "为什么这样设计？" | "运行时发生什么？" | "怎样写合法？" |
| 可证伪性 | 可讨论、可权衡 | 可通过实验验证 | 可通过编译器验证 |
| 陷阱位置 | `## 反模式` | `## 理解与细节` | `## 理解与细节` |

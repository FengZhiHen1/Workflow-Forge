# 领域配置接口规范 (Domain Config Interface Specification)

## 设计目标

本工作流**彻底独立于具体学科领域**。任何符合本接口规范的领域配置均可被动态加载，无需修改工作流代码或 Skill 逻辑。

> 新增一个领域 = 在 `domain-config/` 下创建一个新目录并按本规范填充文件，工作流即可自动识别并加载。

## 目录结构（任何领域必须遵循）

```
domain-config/
├── README.md                     # 本文件：接口规范
├── {domain}/                     # 领域目录（如 math、programming、physics）
│   ├── atom-classification.md    # 必须：原子分类体系、Callout 映射、Mermaid 规范、命名后缀
│   ├── format-contract.md        # 必须：格式契约（frontmatter、Callout、双链、标题等）
│   └── categories/
│       └── {type}.md             # 必须：每个 YAML type 对应一个写作规范文件
```

## 必须文件详解

### 1. atom-classification.md（原子分类体系）

该文件是领域的**核心元数据**，Skill 通过读取它动态了解该领域的全部类型系统和渲染规则。

**必须包含的章节**：

#### 1.1 分类总表

一个 Markdown 表格，列至少包含：

| 列名 | 说明 |
|------|------|
| 类别 | 中文名称 |
| 英文 | 英文标识（用于日志/调试） |
| YAML type | **关键**：写入笔记 frontmatter `type` 字段的值 |
| Callout | 首段 Callout 的类型，如 `[!abstract]`、`[!info]` |
| 语义说明 | 一句话描述该类别的核心语义 |
| Mermaid 节点形状 | 该类别在 Mermaid 图中的节点形状 |

> **唯一性约束**：`YAML type` 列的值在同一领域内必须唯一，且与 `categories/` 下的文件名一一对应。

#### 1.2 各类别详细说明

每个类别必须有独立的 `###` 子节，包含：
- **语义**：该类别的核心含义
- **典型示例**：2-3 个例子
- **判定标准**：如何判定一个知识点属于该类别
- **与其他类别的区分**：边界判定

#### 1.3 陷阱的融入策略（如适用）

说明该领域如何处理陷阱/反例/边界情况：
- 陷阱是否独立成类？
- 如果不独立，嵌入到哪些类型的哪个位置？
- 使用什么 Callout 类型？
- 代码/公式是否允许折叠？

#### 1.4 主从关系判定准则

说明 MOC 原子点列表中 4 空格缩进从属关系的判定规则：
- 什么关系构成"子项"？
- 什么情况下即使存在服务关系也应独立成一级列表？

#### 1.5 Mermaid 节点形状规范（必须）

一个 Markdown 表格，列：

| 知识点类别 | 形状 | Mermaid 语法 | 示例 |
|-----------|------|-------------|------|
| {type} | {形状名} | `{语法}` | `{示例}` |

**可用形状**：
- 矩形：`[["双链名"]]`
- 菱形：`{"双链名"}`
- 圆形：`(("双链名"))`
- 六边形：`{{"双链名"}}`
- 圆角矩形：`("双链名")`

#### 1.6 原子点命名后缀规范（必须）

一个 Markdown 表格，列：

| 类别 | 后缀 | 示例 |
|------|------|------|
| {type} | `{后缀}` | `{示例}` |

**命名铁律**（所有领域通用）：
1. **严禁编号**：禁止 `性质 1.1`、`Definition 1` 等形式
2. **学术描述性**：名称应准确反映知识内涵
3. **唯一性**：同一 Vault 内双链名必须唯一
4. **后缀一致性**：名称后缀必须与 YAML `type` 和 Callout 类型一致

### 2. format-contract.md（格式契约）

该文件定义该领域下所有 Obsidian 笔记的格式规则。

**必须包含的章节**：

#### 2.1 文件 Frontmatter 规范

- YAML frontmatter 的完整字段列表
- 每个字段的：是否必填、取值范围、示例
- 不同 `type` 的字段差异（如 programming 的 `library` 仅在 `type: API` 时必填）

#### 2.2 Callout 映射表

一个 Markdown 表格，明确每种类型的首段 Callout：

| 类型 | Callout 语法 | 折叠 |
|------|-------------|------|
| {type} | `> [!xxx] 类型：[名称]` | 是/否 |

#### 2.3 类型特定的格式规则

- 数学领域：LaTeX 规范、公式包裹规则、高亮避让
- 编程领域：代码块规范、环境标注、代码折叠策略
- 其他领域：自定义的格式规则

#### 2.4 双链规范

- `[[]]` 的基本规则
- 外部引用标注方式
- 跨课程引用格式

#### 2.5 标题层级规范

- MOC 文件的 H1/H2 用途
- 原子笔记文件的 H1/H2/H3 用途
- 禁止行为（如原子笔记中禁止 H1 滥用）

### 3. categories/{type}.md（类别写作规范）

**文件名必须与 `atom-classification.md` 分类总表中的 `YAML type` 值完全一致**。

例如：
- math 领域有 `定义`、`定理`、`性质`、`方法` → 文件名为 `definition.md`、`theorem.md`、`property.md`、`method.md`
- programming 领域有 `语法`、`语义`、`API`、`惯用法` → 文件名为 `syntax.md`、`semantics.md`、`api.md`、`idiom.md`

**必须包含的内容**：

1. **适用分类**：YAML `type` 值和 Callout 类型
2. **内容布局**：完整的笔记模板（含 frontmatter 示例），必须按此顺序
3. **各节写作要求**：每个 `##` 和 `###` 子节的详细要求
4. **质量检查清单**：该类型的必填检查项（复选框列表）

## 领域发现机制

工作流启动时，执行以下步骤动态发现可用领域：

1. **扫描目录**：列出 `references/domain-config/` 下所有子目录（排除本 `README.md`）
2. **验证完整性**：对每个子目录检查：
   - `atom-classification.md` 是否存在
   - `format-contract.md` 是否存在
   - `categories/` 目录是否存在
   - `categories/` 下的文件是否与 `atom-classification.md` 分类总表中的 `YAML type` 一一对应
3. **报告可用领域**：向用户列出所有通过验证的领域
4. **用户选择**：用户指定目标领域，工作流加载对应配置

### 领域配置缺失处理

若用户指定的领域：
- **不存在**：报告错误，列出当前可用领域清单
- **不完整**（缺少必需文件）：报告具体缺失项，提示用户补充
- **categories 与 atom-classification.md 不一致**：报告不一致项（如某 type 有规范文件但分类表未声明，或分类表声明了 type 但缺少规范文件）

## 兼容性保证

### 向后兼容

新增领域不会影响已有领域的运行。各领域的配置相互隔离。

### Skill 通用化保证

所有 Skill 必须：
1. **不内置任何领域假设**：不能硬编码任何特定领域的类型名、Callout 类型或格式规则
2. **运行时读取领域配置**：所有类型相关的判定、映射、规范均在运行时从 `atom-classification.md` + `format-contract.md` + `categories/{type}.md` 读取
3. **优雅降级**：若领域配置中某节缺失，Skill 应跳过相关检查而非崩溃

# API 类原子笔记写作规范 (API Note Specification)

## 适用分类

YAML `type: API`，Callout `> [!tip] API：[名称]`。

> API 笔记记录接口契约——只有"大体量"（完整生命周期模型）和"易错体量"（行为反直觉）才建独立原子笔记；普通 API 在惯用法或项目笔记中以代码块引用。

## 各节写作要求

### `> [!tip] API：[名称]`
- **内容**：一句话归纳——接口名 + 核心功能 + 最重要的契约边界
- **示例**："`std::vector::emplace_back`：在尾部原地构造元素，避免临时对象的拷贝/移动。关键契约：若发生重新分配，所有迭代器、指针、引用均失效。"
- **注意**：不要在此处展开完整签名，签名放在独立的 `## 接口契约` 节

### `## 接口契约`
- **签名**：保留原语言的函数/方法签名风格
- **参数表**：每个参数的"类型 + 约束 + 说明"
- **返回值**：正常和特殊情况都要覆盖
- **异常**：什么条件下会发生异常/错误，异常类型

### `## 生命周期与状态`（如适用）
- **用途**：当 API 涉及对象生命周期、迭代器失效、资源管理时使用
- **重点**：明确标注"什么操作会导致什么失效"
- **示例**：`std::vector` 的重新分配导致迭代器失效；Python `list` 的遍历中修改导致运行时错误

### `> [!warning] 陷阱`
- **铁律**：代码**禁止折叠**
- **重点**：
  - 行为反直觉的地方（如 `remove` 不真正删除元素）
  - 迭代器/指针/引用失效场景
  - 资源管理义务（谁负责释放？）
  - 线程安全问题

### `## 理解与细节`
- **设计位置**：该 API 在库整体架构中的角色
- **对比**：与功能相似 API 的取舍（如 `push_back` vs `emplace_back`）
- **性能**：时间复杂度、空间复杂度、隐藏开销

## API 独立成篇的判定标准

| 维度 | 独立成篇 | 不独立，在惯用法/项目笔记中引用 |
|------|----------|-------------------------------|
| 生命周期 | 有复杂的生命周期模型 | 简单的一次性调用 |
| 行为反直觉 | 有迭代器失效、隐藏拷贝等陷阱 | 行为直观，一看就懂 |
| 异常体系 | 异常条件复杂，容易遗漏 | 不会抛异常或异常条件单一 |
| 版本差异 | 不同版本行为差异大 | 各版本行为一致 |

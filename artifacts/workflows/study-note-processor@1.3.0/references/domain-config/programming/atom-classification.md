# 编程原子知识点分类体系 (Atom Classification System)

## 概览

本文件定义编程学科中原子知识点的分类体系。每个知识点按其行为语义被归入以下类别之一，该分类决定其在 Obsidian 中的 Callout 类型、YAML frontmatter 的 `type` 字段值，以及写作规范。

编程笔记以**行为驱动**为核心哲学——记录的不是"代码长什么样"，而是"代码在特定环境下会表现出什么行为，以及为什么"。

## 分类总表

| 类别 | 英文 | YAML type | Callout | 语义说明 | Mermaid 节点形状 |
|------|------|-----------|---------|---------|-----------------|
| 语法 | Syntax | `语法` | `[!abstract]` | 怎样写是合法的？语言规则与文法构造 | `[[]]`（矩形） |
| 语义 | Semantics | `语义` | `[!info]` | 运行期实际发生什么？行为保证与边界 | `{}`（菱形） |
| API | API | `API` | `[!tip]` | 接口契约与生命周期边界 | `[[]]`（矩形） |
| 惯用法 | Idiom | `惯用法` | `[!info]` | 特定场景下的最佳代码模式 | `[[]]`（矩形） |
| 工具链 | Toolchain | `工具链` | `[!todo]` | 编译器/解释器/包管理器如何处理代码 | `[[]]`（矩形） |
| 原则 | Principle | `原则` | `[!abstract]` | 语言为什么这样设计？深层设计动机 | `{{}}`（六边形） |
| 对比 | Comparison | `对比` | `[!warning]` | 跨语言/跨版本的差异与迁移指南 | `[[]]`（矩形） |

## 关键约束

- **API 不盲目原子化**：只有"大体量"（完整生命周期模型，如 `std::vector`）和"易错体量"（行为反直觉，如 `remove` + `erase` 惯用法）才建独立原子笔记；普通 API 在惯用法或项目笔记中以代码块引用。
- **对比受限独立**：一般差异作为语法/语义/API 笔记的 `## 版本演进` 或 `## 跨语言对比` 子章节；仅在"大模块级"跨语言/跨版本专题时才独立成篇。

## 各类别详细说明

### 语法 (Syntax) — `[!abstract]`

**语义**：回答"怎样写是合法的？"记录语言规则、文法构造、合法写法与非法写法的边界。

**典型示例**：
- Python 列表推导式的语法规则
- C++ 模板特化的语法形式
- Rust 所有权转移的语法标记

**判定标准**：
- 是否在描述"怎样写是合法的/非法的"？
- 是否回答"XX 语法长什么样？"这一形式问题？
- 是否与编译器/解释器的解析行为直接相关？

**与语义的关系**：
- **简单绑定 → 融合笔记（约 70%）**：语法笔记为主体，语义作为 `## 运行期语义` 子章节。适用于语义可在 3 句话内说清、且仅绑定单一语法点的知识。
- **复杂交互 → 分离笔记（约 30%）**：语义独立成篇，通过双链关联多个语法笔记。适用于语义涉及多语法点交互（如 C++ 完美转发 = 模板推导 + 引用折叠 + `std::move`）。

**注意事项**：
- 语法无"对错"之分，但需注意不同标准/版本的语法差异
- 一个语法点可能在不同语言版本中有不同表现，历史差异在正文 `## 版本演进` 中展开

### 语义 (Semantics) — `[!info]`

**语义**：回答"运行期实际发生什么？"记录代码在特定环境下的行为保证、执行顺序、内存模型等。

**典型示例**：
- Python "赋值即引用"的语义保证
- C++ 移动语义的运行期行为
- JavaScript 事件循环的语义模型

**判定标准**：
- 是否在描述"执行时会发生什么"？
- 是否涉及内存、变量、状态的变化？
- 是否具有跨语法点的通用行为保证？

**与语法的区分**：语法关注"合法形式"，语义关注"执行行为"。如果某知识点核心在"运行期发生什么"而非"怎么写"，它应当是语义。

### API (API) — `[!tip]`

**语义**：记录接口契约——输入输出、前置条件、后置条件、生命周期、异常行为。

**典型示例**：
- `std::vector` 的内存重新分配策略与迭代器失效规则
- Python `requests.get()` 的异常体系与超时行为
- Rust `std::sync::Arc` 的引用计数语义

**判定标准**：
- 是否在描述某个库/框架/标准库接口的契约边界？
- 是否涉及"调用后会发生什么"（包括异常情况）？
- 是否是"易错体量"——行为反直觉、生命周期复杂？

**注意事项**：
- 普通 API 用法在惯用法笔记中以代码块引用即可，不必独立成篇
- 只有涉及复杂生命周期、迭代器失效、异常边界等"行为反直觉"的 API 才需要独立原子笔记

### 惯用法 (Idiom) — `[!info]`

**语义**：在特定场景下"应该怎样写"的代码模式。强调**实践操作**而非理论命题。

**典型示例**：
- C++ `remove` + `erase` 惯用法
- Python 上下文管理器 `with` 惯用法
- Go 错误处理 `if err != nil` 惯用法

**判定标准**：
- 核心内容是否为"在 XX 场景下，推荐这样写"？
- 是否强调代码模式/写法风格而非语言规则？
- 是否通常附有代码示例说明？

**与语法的区分**：语法是"合法/非法"，惯用法是"好/不好"。惯用法在语法合法的基础上，进一步给出工程实践中的推荐写法。

### 工具链 (Toolchain) — `[!todo]`

**语义**：编译器、解释器、包管理器、调试器等工具如何处理代码，以及环境配置相关的行为。

**典型示例**：
- GCC 的 `-O2` 优化对未定义行为的影响
- Python `pip` 依赖解析策略
- Rust `cargo` 的 feature 标志解析

**判定标准**：
- 是否在描述"工具如何处理代码"？
- 是否涉及编译/链接/打包/部署的行为？
- 是否与特定平台/版本强绑定？

**环境绑定**：工具链笔记必须标注环境信息（`# env: GCC 13.2 / Linux x86_64`），因为工具链行为高度依赖版本和平台。

### 原则 (Principle) — `[!abstract]`

**语义**：回答"语言为什么这样设计？"记录深层设计动机、编程范式约束、以及对应的反模式。

**典型示例**：
- Rust 所有权系统的设计原则（内存安全零成本抽象）
- Python "显式优于隐式"原则
- C++ RAII 资源管理原则

**判定标准**：
- 是否在解释"为什么语言/API 要这样设计"？
- 是否涉及设计权衡（trade-off）和取舍？
- 是否可讨论、可演变（与数学公理的"不证自明"不同）？

**与语义的区分**：语义描述"是什么"，原则描述"为什么"。原则笔记通常引用多个语义/语法笔记来论证设计动机。

**反模式位置**：原则笔记的陷阱放在 `## 反模式` 节中，使用 `> [!warning]`。

### 对比 (Comparison) — `[!warning]`

**语义**：跨语言或跨版本的差异分析，以及迁移指南。

**典型示例**：
- Python 2 vs Python 3 的字符串模型差异
- C++11/14/17/20 的 `auto` 类型推导演进
- Rust 所有权 vs C++ 智能指针的内存管理对比

**判定标准**：
- 核心价值是否是"差异"而非"知识本身"？
- 是否涉及跨语言/跨版本的横向比较？
- 是否是"大模块级"专题（而非某个小知识点的子章节）？

**注意事项**：
- 一般差异应作为语法/语义/API 笔记的 `## 版本演进` 或 `## 跨语言对比` 子章节
- 仅在需要系统级横向比较时才独立成篇
- 对比笔记通常引用大量其他原子笔记作为对比对象

## 陷阱的融入策略

陷阱不独立成类，而是作为**各类型笔记的固定警示模块**：

| 原子类型 | 陷阱位置 | 形式 |
|----------|----------|------|
| 语法/语义/API/惯用法/工具链 | `## 理解与细节` | `> [!warning]` |
| 原则 | `## 反模式` | `> [!warning]` |
| 对比 | `## 常见迁移陷阱` | `> [!warning]` |

**铁律**：`> [!warning]` 中的代码**禁止折叠**，因为陷阱的价值在于"一眼看到错误"。

### 命名铁律
1. **严禁编号**：禁止 `语法 1.1`、`API 1` 等形式
2. **学术描述性**：名称应准确反映知识内涵，而非序号
3. **唯一性**：同一 Vault 内双链名必须唯一（通过学术名称自然保证）
4. **后缀一致性**：名称后缀必须与 YAML `type` 和 Callout 类型一致

## 主从关系判定准则

在 MOC 的原子点列表中，使用 4 空格缩进表达逻辑从属关系。判定 B 是否为 A 的子项：

1. **实现关系**：B 是 A 的具体实现细节（A 是语法规则，B 是其底层语义 → B 缩进于 A 下）
2. **依赖关系**：B 的存在完全依赖 A（A 是 API 接口，B 是其异常行为 → B 缩进于 A 下）
3. **特例关系**：B 是 A 的特殊场景或边界情况（A 是惯用法，B 是其不适用场景 → B 缩进于 A 下）
4. **版本关系**：B 是 A 的特定版本差异（A 是语法，B 是其在新标准中的变化 → B 缩进于 A 下）

**独立判定**：若 B 在后续多处被引用，即使它是为 A 服务的细节，也应作为一级列表独立存在。

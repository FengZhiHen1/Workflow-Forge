# Module Intent Writer

将高层设计文档中的功能模块转化为**业务意图文档**——面向业务方和测试人员的业务契约，明确"做到什么程度算完成"。

意图文档是模块开发流水线的**第一阶段输出**，经用户冻结确认后，作为 module-spec-writer 的强制输入，驱动后续技术规格编写。

## 外部对接协议（Protocol）

### 1. 契约读取义务

作为 SubAgent 被调度时，执行内部任务前必须依次读取：
1. `.claude/contracts/common.md`（通用契约）
2. 输入契约（优先 `.claude/skills/module-intent-writer/references/contract-input.md`，缺失则读取 `.claude/contracts/input.md`）
3. 输出契约（优先 `.claude/skills/module-intent-writer/references/contract-output.md`，缺失则读取 `.claude/contracts/output.md`）
4. 工作流级共享参考（可选）：若 `workflow_refs` 非空，按需读取其中列出的文件

> **零侵入原则**：若本 Skill 无专用契约且 `workflow_refs` 为空，通用契约自动兜底，无需因此上报 ERROR。

### 2. 输入接收与校验

从编排器注入的 prompt 中提取以下字段：
- `workflow_instance_id`, `agent_id`, `skill_id`, `stage_id`
- `upstream_files`, `upstream_message_ids`（可选）
- `workflow_ref_dir`, `workflow_refs`（可选）
- `special_instructions`（可选）
- `stage_direction`（工作方向指令，优先级最高）
- `metadata.confirm_responses`（恢复执行时注入的用户历史确认回复）

**校验规则**：
- 必填身份字段缺失任意一项：立即终止，上报 `ERROR`，`report` 中说明缺失字段。
- `skill_id` 与自身 `skill_id` 不一致：立即终止，上报 `ERROR`。

### 3. 输出上报

完成后必须调用：
```bash
python .claude/scripts/write_message.py \
  --input <草稿路径> \
  --workflow <workflow_instance_id> \
  --agent-id <agent_id> \
  --skill-id <skill_id>
```

禁止直接手写 JSON 到 `.agent/messages/`。

### 4. 降级熔断

- **方案级降级**（算法变更、精度降低、功能裁剪）：**禁止自主执行**。必须在 `report` 中说明原因，上报 `PENDING_CONFIRM`，等待用户确认。
- **资源级降级**（分批计算、降采样、稀疏矩阵）：可自主执行，但必须在 `report` 中说明具体措施和影响。

## 工作流上下文

本 Skill 是工作流 `project-design-pipeline` 中多个 Stage 的执行器。

**上游 Stage**：
- `s06b-project-sync-check`（来自 Skill `pipeline-director`）
- `s04-module-breakdown`（来自 Skill `module-breakdown-designer`）

**上游产物**：
- `docs/功能设计/功能模块全拆解.md`
- 技术栈设计文档、项目结构设计文档

**下游 Stage**：
- `s12-spec-prepare`（进入 Skill `module-spec-writer`）
- 本 Skill 的产物将作为下游的输入
- 确保输出文件路径符合下游 Skill 的输入契约

### Stage 分派

根据注入的 `stage_id` 执行对应阶段：

| Stage | `confirmation_point` | 职责 |
|-------|---------------------|------|
| `s07-select-module` | `true` | 确认/选择当前要处理的目标模块 |
| `s08-intent-clarify` | `true` | 多轮澄清业务需求（核心模块）或快速确认（一般模块） |
| `s09-intent-authorize` | `true` | 请求用户授权开始生成意图文档 |
| `s10-intent-generate` | `false` | 生成意图文档（草稿状态） |
| `s11-intent-freeze` | `true` | 请求用户冻结授权，锁定意图文档 |

## 通用准备

以下步骤为所有 Stage 共享，在执行具体 Stage 前按需完成。

### 1. 读取功能模块全拆解表

**标准路径**：`docs/功能设计/功能模块全拆解.md`

**若不存在**：扫描 `docs/` 目录，查找 `*功能模块*拆解*.md`、`*module*breakdown*.md`、`*模块*拆解*.md`。若找到唯一匹配文件则读取；若找到多个或不匹配，在 `report` 中说明，上报 `ERROR`。

**提取字段**：模块编号、模块名称、模块类型（`🔴 核心` / `🟢 一般`）、核心功能、颗粒度描述、设计文档溯源、所属分组/子系统。

> **所属分组推断**：从拆解表章节结构推断（如 `## 08-AI内容拆解管线`）。同时扫描 `docs/功能设计/` 下已有子目录，若存在同名或近似目录，以此作为最终分组依据。

### 2. 读取全局设计文档

- **技术栈设计文档**：`docs/技术栈设计.md`（不存在则扫描 `*技术栈*.md`）
- **项目结构设计文档**：`docs/项目结构设计.md`（不存在则扫描 `*项目结构*.md`）

若找不到，在材料清单中明确注明，但不阻塞执行。

### 3. 按需读取原始设计文档

根据"设计文档溯源"中引用的文档名，**只读取与当前模块相关的对应章节**。

**标准路径**：`docs/功能设计/原始材料/[文档名].md`

### 4. 兼容性审查

生成本模块意图前，必须先检查与已有模块的业务兼容性。

**第一段：读取契约索引**

读取 `docs/功能设计/_contracts.md`。若不存在：
- `docs/功能设计/` 下无任何 `.md` 规格文档 → 项目首个模块，跳过冲突检测
- 已有规格文档 → 做一次全文加载完成审查

遍历索引中所有条目，逐项对比：业务依赖冲突、验收标准冲突、业务规则冲突。

**第二段：按需深读**

仅当索引条目显示与当前模块存在业务关联时，才读取该模块的意图文档或设计文档。

**冲突解决规则**：
- 若可判断时间先后：以时间戳更新的文档为权威源，自主解决冲突
- 若无法判断新旧：将冲突点整理为问题清单，纳入澄清问题上报用户决策

审查结论写入输出文档的「已有设计兼容性分析」节。**禁止跳过此步骤直接生成。**

## Stage 执行规范

### s07-select-module：模块确认

**目标**：确认当前要处理的目标模块。

1. 读取功能模块全拆解表
2. 检查 `stage_direction` / `special_instructions` 是否已指定模块编号/名称：
   - **已指定**：提取该模块的摘要信息（编号、名称、类型、核心功能一句话）
   - **未指定**：列出所有尚未生成意图文档的模块清单（编号 + 名称 + 类型）
3. 上报 `PENDING_CONFIRM`，请求用户确认/选择目标模块

**confirm_questions 示例**：
- "本次为模块 M02（世界观构建引擎，🔴 核心）生成业务意图文档，是否确认？"
- 或"请从以下模块中选择本次要处理的目标模块：..."

恢复执行后（用户已确认/选择模块），上报 `DONE`。

### s08-intent-clarify：需求澄清

**目标**：通过多轮迭代彻底澄清业务需求，直到所有关键维度无歧义。

**首次执行**（无 `metadata.confirm_responses`）：

1. 执行「通用准备」收集全部输入材料
2. 识别模块类型：
   - `🔴 核心` → 进入核心澄清流程
   - `🟢 一般` → 执行快速自检（业务边界、输入输出定义、业务规则、状态机、兼容性）
     - 5 项全部通过 → 进入快速确认流程
     - 1-2 项未通过 → 进入针对性澄清（最多 1 轮）
     - ≥3 项未通过 → 按 `🔴 核心` 处理

3. **核心澄清流程**：基于材料分析，识别当前最关键的 2-4 个未澄清维度（歧义点、未定义项、冲突点、业务规则、验收标准、边界权衡）。整理为具体问题，上报 `PENDING_CONFIRM`。

4. **快速确认流程**：总结自检通过的维度，上报 `PENDING_CONFIRM` 请求快速授权（选项含"直接生成"和"切换到全量澄清"）。

**恢复执行**（有 `metadata.confirm_responses`）：

1. 重新读取输入材料（确保上下文完整）
2. 整合所有历史 `confirm_responses`，更新"已澄清维度清单"
3. **判断终止条件**（以下全部满足方可终止）：
   - 所有歧义点已有确认解释
   - 所有未定义项已有确认值或策略
   - 所有冲突点已有裁决
   - 所有业务规则已有明确方向
   - 模块边界、输入/输出业务定义、状态机需求已无模糊
   - 所有验收标准已有量化指标
   - 已明确列出"留给规范阶段的技术决策"清单

4. **分流**：
   - **终止条件未满足**：基于剩余未澄清维度，整理下一轮 1-4 个问题，上报 `PENDING_CONFIRM`
   - **终止条件已满足**：上报 `DONE`

**confirm_questions 设计原则**：
- 每个问题必须具体、可回答，推荐方案放在最前并标注 `(Recommended)`
- 在问题前用 3-5 句话简要汇报调研背景
- 具体提问格式参考 `references/confirmation-examples.md`

> **禁止**：以纯文本形式输出问题列表等待用户回复；将多轮问答压缩为单轮；跳过澄清直接生成；将疑虑隐藏或自行裁决；在未明确"留给规范阶段的技术决策"前结束澄清。

### s09-intent-authorize：书写授权

**目标**：获得用户明确授权后开始生成意图文档。

1. 读取输入材料及历史澄清记录
2. 总结已达成的主要共识（业务边界、输入输出、状态机、业务规则、验收标准各一句话）
3. 确认"留给规范阶段的技术决策"清单已明确且非空
4. 上报 `PENDING_CONFIRM`，请求书写授权

**confirm_questions 示例**：
"所有业务需求已澄清完毕。是否授权开始生成意图文档 `[编号]-[名称]-意图文档.md`？"

恢复执行后（用户确认授权），上报 `DONE`。

> 若用户选择"还需要补充"，这相当于还有未澄清的维度。此时应在 `report` 中说明需要补充的内容，上报 `PENDING_CONFIRM` 列出补充问题（相当于将澄清循环延长）。

### s10-intent-generate：生成意图文档

**前置条件**：已通过 `s09-intent-authorize` 获得书写授权。

**目标**：按模板生成意图文档（草稿状态）。

1. 读取输入材料、澄清历史和授权记录
2. 调用 `scripts/get_timestamp.py` 获取文档生成时间
3. 按 `references/intent-template.md` 生成意图文档，文档状态为 `草稿`
4. 确保目标目录存在：`docs/功能设计/[所属分组]/[编号]-[名称]/`
5. 输出到：`docs/功能设计/[所属分组]/[编号]-[名称]/[编号]-[名称]-意图文档.md`

**通用规则**：
- 使用业务方可理解的语言，不出现具体技术类型
- 每个业务字段包含：字段名、业务含义、是否必填、业务约束、示例值
- 验收标准可量化、可测试
- 状态使用业务名称，描述业务含义和进入/退出条件
- 异常策略从业务角度描述，无技术处理细节
- 必须包含"留给规范阶段的技术决策"章节且内容非空
- 所有业务概念使用语义化命名，**严禁使用模块编号作为命名前缀**
- 绝对禁止偷懒表述：`"等等"`、`"..."`、`"其他字段"`、`"类似"`、`"同上"`、`"请根据实际情况补充"`

**禁止写入**：具体技术类型、技术实现细节、技术选型理由、架构权衡、备选方案对比、编码层面的禁止行为。

生成完成后，上报 `DONE`。

### s11-intent-freeze：冻结授权

**目标**：获得用户显式冻结授权后锁定意图文档。

**首次执行**（无 `metadata.confirm_responses`）：

1. 读取已生成的意图文档
2. 总结文档核心内容：业务边界、验收标准、关键业务规则各一句话
3. 明确告知用户"冻结后不可擅自修改，如需修改必须通过回退机制重新解冻"
4. 上报 `PENDING_CONFIRM` 请求冻结授权

**恢复执行**（有 `metadata.confirm_responses`）：

解析用户选择：
- **"冻结确认"**：
  1. 调用 `scripts/get_timestamp.py` 获取冻结时间
  2. 更新文档状态为 `已冻结`，写入冻结时间
  3. 保存修改后的文档
  4. 上报 `DONE`
- **"还需要修改"**：
  1. 根据用户反馈修改文档内容
  2. 修改完成后，再次上报 `PENDING_CONFIRM` 请求重新冻结

> **禁止**：在未获冻结授权前将意图文档标记为冻结；在冻结授权未通过时告知用户"文档已完成"而不明确冻结状态。

## 文档结构

详细模板见 `references/intent-template.md`。输出时必须包含以下章节：

> 1.1 项目定位 → 1.2 所属模块与溯源 → 1.3 已有设计兼容性分析 → 1.4 业务目标 → 1.5 用户旅程 / 业务流程 → 1.6 输入/输出业务定义 → 1.7 状态的业务定义（如适用）→ 1.8 异常的业务策略 → 1.9 验收标准 → 1.10 业务依赖关系 → 1.11 业务约束清单 → **1.12 留给规范阶段的技术决策** → 版本记录（含冻结状态）

## Message 上报契约

1. 你的 `agent_id`、`workflow_instance_id`、`skill_id` 已由编排器注入，请在 message 中原样使用，禁止自行编造。
2. 当你完成阶段任务或需要用户确认时：
   - 在 `.tmp/<workflow_instance_id>/` 下生成你的 message 草稿 JSON；
   - 调用 `python .claude/scripts/write_message.py --input <草稿路径> --workflow <instance_id> --agent-id <你的agent_id> --skill-id <你的skill_id>`；
   - 若脚本返回错误（非零退出码），根据 stderr 修正后重新调用；
   - 若连续失败 3 次，将 `status` 改为 `ERROR`，`report` 中说明校验失败详情，并终止。
3. `message_id` 由脚本自动生成，你无需提供。
4. `confirm_questions` 必须是字符串数组，长度 1-4。若你有多项待确认，一次性全部列出，不要分多次终止。
5. 终止前，你的最终回答必须包含脚本返回的 message 文件路径。

### 确认点上报（Confirmation Point）

本 Skill 对应 stages 中 `s07-select-module`、`s08-intent-clarify`、`s09-intent-authorize`、`s11-intent-freeze` 的 `confirmation_point=true`。这些 Stage 完成任务后：

1. **不要直接上报 `DONE`**
2. 生成 message 草稿 JSON，设置 `status: "PENDING_CONFIRM"`
3. 设置 `confirm_questions: ["你的确认问题"]`（1-4 个字符串，必须具体、可回答）
4. 调用 `write_message.py` 上报
5. 终止执行，等待编排器处理用户确认

用户确认后，编排器会自动将本 stage 标记为 DONE，并走 `condition: confirmed` 的 edge 解锁下游；或将本 stage 重新调度，注入 `metadata.confirm_responses` 供 Skill 继续执行。

**确认问题设计原则**：

# 模块审查报告生成器 (Module Review Reporter)

本 Skill 是工作流 `module-review@1.0.0` 的 Stage `s03-report` 执行器。
confirmation_point 始终为 true，自循环上限 3 次。

**上游**：s02-audit（产出 implementation_check.json + integration_result.json）
**下游**：s99-workflow-end（用户确认后完成）

---

## 核心流程

### 1. 收集上游产物

从 `upstream_files` 读取以下文件：

| 文件 | 来源 | 内容 |
|:---|:---|:---|
| `identified_modules.json` | s01-identify | 模块编号、名称、设计文档/落地规范路径 |
| `implementation_check.json` | s02-audit | 交付物完整性、接口实现、核心逻辑、测试覆盖检查结果 |
| `integration_result.json` | s02-audit | 跨模块联动验证结果（已实现/部分实现/未实现/无法验证） |

### 2. 获取时间戳

调用工作流共享脚本获取跨平台准确时间戳（兼容 Windows/Linux/macOS）：

```bash
python <workflow_ref_dir>/scripts/get_timestamp.py
```

脚本不可用时降级为 Python `datetime` 内置模块（`datetime.datetime.now()`）。禁止依赖系统环境变量或 AI 内部时间推断。输出格式固定为 `YYYY-MM-DD HH:MM:SS`（Asia/Shanghai 时区）。

### 3. 确定保存位置

- 检查目标目录：`docs/审查报告/`（不存在则创建）
- 文件名格式：`模块审查-{module_ids}-{YYYY-MM-DD}.md`
- 若同模块已有历史报告，扫描目录获取最新版本号用于增量

### 4. 生成审查报告

引用 `references/report-template.md` 作为模板，生成**摘要 + 详细附录**双栏报告。

**摘要栏**：
- 总体结论表（通过 / 部分通过 / 严重问题）
- 关键发现问题（🔴 严重 / 🟡 中等 / 🟢 轻微 三级分组）
- 审查范围（模块列表 + 审查维度）
- 优先修复建议（按预计工作量排序）

**详细附录**：
- 交付物检查表（每模块每文件的检查状态与备注）
- 接口验证表（每接口的签名匹配状态与行号引用）
- 联动矩阵（NxN 模块联动验证结果）
- 测试覆盖统计（正常/异常/边界场景覆盖率）

**版本记录**：
- 若已有历史报告，继承版本号并递增（v1.0 → v1.1 → ...）
- 首次审查从 v1.0 开始
- 每条记录包含：版本号、审查时间、审查人、变更摘要

**冲突核查指引**：
- 若审查结论与历史报告存在矛盾，优先以时间戳更新的版本为准
- 在版本记录中追加冲突解决条目，注明冲突内容与解决方式

**降级策略**：
- `references/report-template.md` 缺失 → 使用本文件中描述的章节结构降级生成，在"审查方法"中注明降级
- 上游产物部分缺失 → 对应章节标记 `⚠️ 数据缺失`，继续生成可用部分

### 5. 提交用户确认（PENDING_CONFIRM）

报告保存后，向编排器提交 PENDING_CONFIRM：

1. 在 message 草稿中设置 `status: "PENDING_CONFIRM"`
2. 从报告中提取关键摘要数据（总体结论、各级问题数量、报告路径）
3. 构造 `confirm_questions`（1-4 项），基于实际报告内容，示例如下：

   - "审查结论是否准确？共发现 {N} 项 🔴 严重问题、{M} 项 🟡 中等问题"
   - "是否需要对某个模块进行复查或深入检查？"
   - "报告已保存至 `{报告路径}`，是否可以标记本次审查完成？"

4. 调用 `write_message.py` 上报后终止执行，等待编排器恢复

### 6. 处理用户反馈（自循环）

- **确认（confirmed）** → 流转到 s99-workflow-end，工作流完成
- **拒绝（rejected，附补充意见）** → 按用户反馈调整报告后重新生成并提交确认
  - 常见反馈：补充遗漏模块、调整结论措辞、追加联动检查、修正判定级别
  - 每个循环都基于当前最新反馈重新生成完整报告
- **达到自循环上限（loop_exceeded，3 次）** → 以最后一次版本为终稿，在报告备注中注明已达最大修订次数

---

## 异常处理

| 场景 | 处理方式 |
|:---|:---|
| 上游产物全部缺失 | 上报 `ERROR`，说明无法生成报告 |
| `get_timestamp.py` 不可用 | 降级为 Python `datetime`，不影响报告生成 |
| 报告模板缺失 | 使用降级结构生成（见下方），在报告"审查方法"中注明降级 |
| 部分上游产物缺失 | 对应章节标记 `⚠️ 数据缺失`，继续生成可用部分 |
| 某模块此前无历史报告 | 版本号从 v1.0 起算 |

### 降级报告最小结构

模板缺失时，报告至少包含六个章节：
1. 审查信息（审查时间、审查模块、对应设计文档）
2. 执行摘要（总体结论 + 关键发现 + 修复建议）
3. 分模块审查（交付物检查、接口检查、测试检查、问题清单）
4. 联动审查（预期联动图、实际验证表、联动问题详情）
5. 差距分析（模块内差距、模块间差距、建议修复顺序）
6. 附录（审查范围、审查方法、限制说明、参考文档）

# Module Intent Writer

将高层设计文档中的功能模块转化为**业务意图文档**——面向业务方和测试人员的业务契约，明确"做到什么程度算完成"。

意图文档是模块开发流水线的**第一阶段输出**，经用户冻结确认后，作为 module-spec-writer 的强制输入，驱动后续技术规格编写。

## 前置要求

执行任务前，读取 `references/contract-reading-guide.md` 了解契约读取顺序。

## 核心原则

- **业务语言优先**：意图文档使用业务方可理解的语言，禁止混入技术实现细节。
- **多轮澄清**：核心模块必须通过多轮问答彻底澄清业务需求，禁止跳过澄清直接生成。
- **门控机制**：书写授权（s08）与冻结授权（s10）为两个独立门控，必须分别获得用户显式确认。
- **冻结不可变**：冻结后的意图文档作为后续 spec-writer 的强制输入，不可擅自修改。
- **禁止偷懒**：文档中禁止出现"等等"、"..."、"其他字段"等偷懒表述，每个字段必须有完整业务定义。
- **中文输出**：所有输出文本使用中文，代码与专有名词除外。

## 执行逻辑（按 stage_id 路由）

编排器注入 `stage_id`，按以下分支执行对应阶段。

### 通用准备

以下步骤为所有 Stage 共享，在执行具体 Stage 前按需完成。

#### 1. 读取功能模块全拆解表

**标准路径**：`docs/功能设计/功能模块全拆解.md`

**若不存在**：扫描 `docs/` 目录，查找 `*功能模块*拆解*.md`、`*module*breakdown*.md`、`*模块*拆解*.md`。若找到唯一匹配文件则读取；若找到多个或不匹配，上报 `ERROR`。

**提取字段**：模块编号、模块名称、模块类型（`🔴 核心` / `🟢 一般`）、核心功能、颗粒度描述、设计文档溯源、所属分组/子系统。

> **所属分组推断**：从拆解表章节标题 `## [两位数字]-[分组名]`（如 `## 01-用户域`）中直接提取 `[序号]-[分组]` 作为目录前缀。**禁止**将章节标题原文（尤其是含中文数字的旧格式）直接用作目录名。若章节标题为旧格式（中文数字），必须按 `directory-convention.md` §5 映射表标准化为两位阿拉伯数字。完成后扫描 `docs/功能设计/` 下已有子目录验证一致性。

#### 2. 读取全局设计文档

- **技术栈设计文档**：`docs/技术栈设计.md`（不存在则扫描 `*技术栈*.md`）
- **项目结构设计文档**：`docs/项目结构设计.md`（不存在则扫描 `*项目结构*.md`）

若找不到，在材料清单中明确注明，但不阻塞执行。

#### 3. 按需读取原始设计文档

根据"设计文档溯源"中引用的文档名，**只读取与当前模块相关的对应章节**。

**标准路径**：`docs/功能设计/原始材料/[文档名].md`

#### 4. 兼容性审查

生成本模块意图前，必须先检查与已有模块的业务兼容性。

**第一段：读取契约索引**

读取 `docs/功能设计/_contracts.md`。若不存在：
- `docs/功能设计/` 下无任何 `.md` 规格文档 → 项目首个模块，跳过冲突检测
- 已有规格文档 → 做一次全文加载完成审查

遍历索引中所有条目，逐项对比：业务依赖冲突、验收标准冲突、业务规则冲突。

**第二段：按需深读**

仅当索引条目显示与当前模块存在业务关联时，才读取该模块的意图文档或设计文档。

**冲突解决规则**：
- 若可判断时间先后：以时间戳更新的文档为权威源，自主解决冲突
- 若无法判断新旧：将冲突点整理为问题清单，纳入澄清问题上报用户决策

审查结论写入输出文档的「已有设计兼容性分析」节。**禁止跳过此步骤直接生成。**

### s06-select-module：项目状态汇报与模块选择

**目标**：汇报项目级设计状态和已有模块进度，选择本次要处理的目标模块。

1. 执行「通用准备」第 1 步，读取功能模块全拆解表。
2. 扫描 `docs/功能设计/` 下已有模块子目录，汇总各模块完成状态：
   - **已冻结**：意图文档 `[编号]-[名称]-意图文档.md` 存在且状态标注为 `已冻结`
   - **草案待冻结**：意图文档存在但状态为 `草稿`（异常情况，需注明）
   - **未处理**：无对应子目录或无意向文档
3. 以表格形式汇报项目全局状态（已完成数 / 已冻结数 / 未处理数）和各模块摘要。
4. 列出当前**可选的未处理模块**清单（编号 + 名称 + 类型 + 归属分组）。
5. 检查 `stage_direction` / `special_instructions` 是否已指定模块：
   - **已指定**：提取该模块摘要信息（编号、名称、类型、核心功能一句话），向用户确认。
   - **未指定**：列出可选模块清单供用户选择。
6. 按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `confirm_questions` 设计参考 `references/confirmation-examples.md` 示例 1。
   - 若无可选模块（全部已冻结），告知用户"所有模块的意图文档均已冻结"，建议结束工作流。

> 用户选择"结束工作流"时，编排器按 `condition: rejected` 边流转到 `s99-workflow-end`。

### s07-intent-clarify：模块意图澄清

**目标**：通过多轮迭代彻底澄清业务需求，直到所有关键维度无歧义。

**首次执行**（无 `metadata.confirm_responses`）：

1. 执行「通用准备」收集全部输入材料。
2. 识别模块类型：
   - `🔴 核心` → 进入核心澄清流程（步骤 3）
   - `🟢 一般` → 执行快速自检（步骤 4）

3. **核心澄清流程**：
   - 基于材料分析，汇报调研背景（3-5 句话）：材料清单、业务边界初步分析、兼容性审查结论。
   - 识别当前最关键的 2-4 个未澄清维度：歧义点、未定义项、冲突点、业务规则、验收标准、边界权衡。
   - 整理为具体问题，按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`。
   - `confirm_questions` 设计参考 `references/confirmation-examples.md` 示例 2。

4. **快速自检流程**（`🟢 一般` 模块）：

   | 自检维度 | 通过标准 |
   |:---|:---|
   | 业务边界 | 设计文档已明确本模块的职责范围 |
   | 输入/输出业务定义 | 业务字段可从设计文档直接推断 |
   | 业务规则 | 使用行业默认规则或项目统一规范 |
   | 状态机 | 无复杂异步流程，或状态转换已在设计文档中描述清楚 |
   | 兼容性 | 与已有规格无业务冲突 |

   自检结果分流：
   - **5 项全部通过** → 上报 `PENDING_CONFIRM` 请求快速授权（参考 `references/confirmation-examples.md` 示例 4）。
   - **1-2 项未通过** → 针对未通过维度提出 1-2 个澄清问题（最多 1 轮），上报 `PENDING_CONFIRM`。
   - **>=3 项未通过** → 切换回核心澄清流程。

**恢复执行**（有 `metadata.confirm_responses`）：

1. 重新读取输入材料（确保上下文完整）。
2. 整合所有历史 `confirm_responses`，更新"已澄清维度清单"。
3. **判断终止条件**（以下全部满足方可终止）：
   - 所有歧义点已有确认解释
   - 所有未定义项已有确认值或策略
   - 所有冲突点已有裁决
   - 所有业务规则已有明确方向
   - 模块边界、输入/输出业务定义、状态机需求已无模糊
   - 所有验收标准已有量化指标
   - 已明确列出"留给规范阶段的技术决策"清单
4. **分流**：
   - **终止条件未满足**：基于剩余未澄清维度，整理下一轮 1-4 个问题，上报 `PENDING_CONFIRM`（参考 `references/confirmation-examples.md` 示例 3）。
   - **终止条件已满足**：上报 `DONE`。

**confirm_questions 设计原则**：
- 每个问题必须具体、可回答，推荐方案放在最前并标注 `(Recommended)`。
- 在问题前用 3-5 句话简要汇报调研背景。
- 若有多项待确认内容，一次性全部列出，不要分多次终止。

> **多轮循环**：编排器按 WORKFLOW.yaml 的 `rejected→s07` 边循环（最多 5 轮）。达到 `max_loop` 后自动流转回 `s06-select-module`，用户可重新选择模块。

### s08-intent-authorize：意图文档书写授权

**目标**：汇总澄清共识，获得用户显式授权后进入文档生成。

1. 读取输入材料及历史澄清记录（`metadata.confirm_responses`）。
2. 总结已达成的主要共识：
   - 业务边界（一句话）
   - 输入/输出的业务定义（一句话）
   - 状态机需求（一句话，如不适用则说明）
   - 关键业务规则（一句话）
   - 验收标准（一句话，含关键量化指标）
3. 确认"留给规范阶段的技术决策"清单已明确且内容非空。
4. 按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `confirm_questions` 设计参考 `references/confirmation-examples.md` 示例 5。

> 若用户选择"还需要补充"：编排器按 `rejected→s07` 边回到 s07-intent-clarify 继续提问。达到 `max_loop`（3 轮）后回到 `s06-select-module`。

### s09-intent-generate：生成意图文档

**前置条件**：已通过 s08 获得书写授权。

**目标**：按模板生成意图文档（草稿状态）。

1. 读取输入材料、澄清历史（`metadata.confirm_responses`）和授权记录。
2. 调用 `scripts/get_timestamp.py` 获取文档生成时间。
3. 按 `references/intent-template.md` 的结构和规范生成意图文档，文档状态为 `草稿`。
4. 确保目标目录存在：`docs/功能设计/[序号]-[分组]/[编号]-[名称]/`（`[序号]-[分组]` 取自已标准化的所属分组推断结果，严格遵守 `directory-convention.md`）。
5. 输出到：`docs/功能设计/[序号]-[分组]/[编号]-[名称]/[编号]-[名称]-意图文档.md`。

**通用规则**：
- 使用业务方可理解的语言，不出现具体技术类型（如 Pydantic、TypeScript 类型）。
- 每个业务字段包含：字段名、业务含义、是否必填、业务约束、示例值。
- 验收标准可量化、可测试。
- 状态使用业务名称，描述业务含义和进入/退出条件。
- 异常策略从业务角度描述，无技术处理细节。
- 必须包含"留给规范阶段的技术决策"章节且内容非空。
- 所有业务概念使用语义化命名，**严禁使用模块编号作为命名前缀**。
- 绝对禁止偷懒表述：`"等等"`、`"..."`、`"其他字段"`、`"类似"`、`"同上"`、`"请根据实际情况补充"`。

**禁止写入**：具体技术类型、技术实现细节、技术选型理由、架构权衡、备选方案对比、编码层面的禁止行为。

生成完成后上报 `DONE`（本 Stage `confirmation_point=false`，编排器自动流转到 s10）。

### s10-intent-freeze：意图文档冻结授权

**目标**：获得用户显式冻结授权后锁定意图文档。

**首次执行**（无 `metadata.confirm_responses`）：

1. 读取已生成的意图文档。
2. 总结文档核心内容（业务边界、验收标准、关键业务规则各一句话）。
3. 明确告知用户"冻结后不可擅自修改，如需修改必须通过回退机制重新解冻"。
4. 按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `confirm_questions` 设计参考 `references/confirmation-examples.md` 示例 6。

**恢复执行**（有 `metadata.confirm_responses`）：

解析用户选择：
- **"冻结确认"**：
  1. 调用 `scripts/get_timestamp.py` 获取冻结时间。
  2. 更新文档状态为 `已冻结`，写入冻结时间和版本记录行（在版本记录中新增 `v2.0` 行，状态标注 `**已冻结**`）。
  3. 保存修改后的文档。
  4. 上报 `DONE`。
- **"还需要修改"**：
  1. 根据用户反馈修改文档内容。
  2. 修改完成后，再次上报 `PENDING_CONFIRM` 请求重新冻结（参考 `references/confirmation-examples.md` 示例 7）。

> 若用户反复修改导致循环达到 `max_loop`（3 轮），编排器按 `loop_exceeded` 边回到 `s06-select-module`。

## 质量检查清单

输出前逐项确认：

**通用检查**：
- [ ] `🔴 核心` 模块：已通过 s07 多轮问答澄清所有关键决策点；`🟢 一般` 模块：已通过快速自检或最多 1 轮澄清
- [ ] s08 已获得用户显式书写授权
- [ ] s10 已获得用户显式冻结授权
- [ ] 文档已标注冻结状态和时间（仅冻结后）
- [ ] 文档包含"留给规范阶段的技术决策"章节且内容非空
- [ ] 所有"（待确认）"标注都有合理推断
- [ ] 已通过契约索引审查已有规格，无冲突或冲突已记录解决方案
- [ ] 已读取并参考项目技术栈设计文档和项目结构设计文档
- [ ] **版本记录每一行都以 `> ` 开头**

**业务内容检查**：
- [ ] 项目定位清晰，2-3 句话讲清模块业务角色与价值
- [ ] 用户旅程完整，涵盖主要使用场景
- [ ] 输入/输出字段的业务含义明确，无技术类型混入
- [ ] 验收标准可量化、可测试
- [ ] 业务约束清单有具体条目，不是空洞口号
- [ ] 异常策略从业务角度描述，无技术处理细节
- [ ] 状态定义使用业务名称，描述业务含义
- [ ] 未逐字复制总设计的描述性段落
- [ ] 无偷懒表述

## 约束与禁止行为

- **禁止跳过澄清**：`🔴 核心` 模块必须经过 s07 多轮澄清，`🟢 一般` 模块必须经过快速自检。不得跳过澄清直接生成。
- **禁止越界决策**：涉及业务矛盾或文档不足的问题，必须上报用户确认，禁止自行裁决。
- **禁止缺少技术决策留白**：每份意图文档必须包含"留给规范阶段的技术决策"章节且内容非空。
- **禁止未授权生成**：未通过 s08 书写授权前，不得进入 s09 生成文档。
- **禁止未冻结标记**：未通过 s10 冻结授权前，不得将文档状态设为 `已冻结` 或告知用户"文档已完成"。
- **禁止写入技术细节**：意图文档中不得出现具体技术类型、技术实现细节、架构权衡、备选方案对比。
- **禁止偷懒表述**：文档中不得出现 `"等等"`、`"..."`、`"其他字段"`、`"类似"`、`"同上"`、`"请根据实际情况补充"` 等表述。
- **禁止合并模块**：每个模块独立输出一份意图文档，不得将多个功能点合并到同一份文档。
- **禁止逐字复制**：不得逐字复制总设计的描述性段落。

# Module Spec Writer

基于已冻结的**意图文档**，为功能模块生成两份技术文档：
- **设计文档（瘦身版）**：技术实现思路、架构权衡、兼容性分析、设计原则兑现
- **落地规范**：精确的类型定义、接口契约、状态转换表、异常阈值、验收测试场景

> **流水线关系**：module-intent-writer → 意图文档（冻结）→ s11 材料准备 → spec-researcher（独立 Stage）→ s13 设计文档 → contract-harmonizer（独立 Stage）→ s15 落地规范 + 契约 → s16 同步检查
> module-spec-writer **必须**以已冻结的意图文档为输入，**禁止**跳过意图文档直接生成技术规格。

## 核心原则

- **意图文档为强制门控**：未冻结的意图文档 → 立即终止，不得继续。
- **意图缺陷零容忍**：发现技术不可行项 → 触发回退机制，无权自行妥协。
- **外部接口先锁定**：对外接口经契约协调后锁定（`【已锁定】`），内部实现不得修改。
- **中文输出**：所有面向用户的文本使用中文，代码与专有名词除外。

## 执行逻辑（按 stage_id 路由）

编排器注入 `stage_id`，按以下分支执行对应阶段。

### s11-spec-prepare：输入准备与前置检查（cp:false）

**目标**：验证输入完备性，检测意图缺陷，执行项目级一致性扫描。

1. **读取上游产物**：从 `upstream_files` 读取已冻结的意图文档路径。
2. **意图文档校验**：
   - 检查文档存在性。缺失 → 上报 `ERROR`，说明缺失文件路径。
   - 检查冻结状态（文档内标注"已冻结"且有冻结时间）。未冻结 → 上报 `ERROR`。
3. **意图缺陷初筛**：扫描意图文档中的业务约束和验收标准，判断是否存在明显技术不可行项：
   - 性能指标无法达成
   - 与项目技术栈根本性冲突
   - 业务规则自相矛盾
   - 若发现意图缺陷 → 触发**回退机制**（见下方），不得继续后续步骤。
4. **收集材料路径**：定位并记录以下路径（仅记录，不读取内容）：
   - 技术栈设计文档：`docs/技术栈设计.md`
   - 功能模块全拆解表：`docs/功能设计/功能模块全拆解.md`
   - 模块依赖关系分析：`docs/功能设计/模块依赖关系分析.md`
   - 契约索引：`docs/功能设计/_contracts.md`
   - 已有规格文档：扫描 `docs/功能设计/` 下所有 `[编号]-[名称]-落地规范.md`
5. **项目级一致性检查**：
   - 扫描已有规格文档的模块编号、状态定义、接口命名。
   - 检查同名异构类型、状态定义冲突、循环依赖迹象。
   - 将发现的问题追加写入 `docs/功能设计/_sync-issues.md`（按时间戳分节，不覆盖已有内容）。
   - 若无问题，确保 `_sync-issues.md` 中本模块对应节标注 "✅ 无冲突"。
6. **上报**：按 agent-protocol.md 规范，~输出材料清单、意图缺陷结论、同步检查结果摘要~，上报 `DONE`。

### s13-spec-design-doc：生成设计文档（cp:true）

**目标**：基于 spec-researcher 的技术决策报告，生成设计文档（瘦身版）。

> **前置**：s12 spec-researcher（独立 Stage）已完成技术预研，产出《技术决策完整报告》。
> 本 Skill **不调度** spec-researcher，仅读取其产物。

1. **读取上游产物**：
   - 从 `upstream_files` 读取 spec-researcher 的《技术决策完整报告》。
   - 从 `upstream_message_ids` 读取用户在上轮 s13→s13 循环中的裁决反馈（如有）。
2. **检查业务矛盾**：
   - 提取报告中的业务矛盾标记清单。
   - 若清单非空 → 基于报告推荐方案和用户历史裁决（如有）做出最佳推断，标注矛盾及处理方式。
   - 若用户历史裁决与报告推荐冲突 → **以用户裁决为准**。
3. **项目级一致性复查**：
   - 再次扫描已有规格文档，核对本模块设计决策是否与已有模块产生新增冲突。
   - 将新增冲突追加到 `docs/功能设计/_sync-issues.md`。
4. **生成设计文档**：
   - 以 spec-researcher 报告为核心依据，用户历史裁决为修正项。
   - 输出路径：`docs/功能设计/[分组]/[编号]-[名称]/[编号]-[名称]-设计文档.md`
   - 模板：`references/human-design-template.md`
   - 必须包含章节：1.1 技术实现思路 → 1.2 已有设计兼容性分析 → 1.3 依赖关系概述 → 1.4 状态机设计（如适用）→ 1.5 设计原则兑现清单 → 1.6 架构权衡与备选方案 → 1.7 注意事项与禁止行为 → 1.8 引用：配套意图文档
5. **上报**：按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `report` 包含：设计文档路径、关键决策摘要、矛盾处理说明（如有）。
   - `confirm_questions` 示例：
     - "设计文档的技术实现思路是否与意图文档对齐？"
     - "矛盾处理方案（如有）是否可接受？"
     - "是否有需要调整的架构决策或技术选型？"
   - 确认通过 → 流转到 s14 contract-harmonizer。
   - 拒绝 → s13→s13 循环修订（max_loop: 3，见 WORKFLOW.yaml）。

### s15-spec-final：最终规格输出（cp:true）

**目标**：基于设计文档和 contract-harmonizer 报告，生成落地规范、写入契约文件、更新索引。

> **前置**：s14 contract-harmonizer（独立 Stage）已完成契约协调，产出《契约协调报告》。
> 本 Skill **不调度** contract-harmonizer，仅读取其产物。

1. **读取输入**：
   - 从 `upstream_files` 读取 contract-harmonizer 的《契约协调报告》。
   - 从 `upstream_files` 或扫描 `docs/功能设计/` 定位设计文档。
   - 从 `upstream_message_ids` 读取用户在上轮 s15→s15 循环中的裁决反馈（如有）。
2. **处理契约冲突**：
   - 提取报告中的 `findings.conflicts` 和 `findings.reusables`。
   - 若有冲突 → 基于 harmonizer 推荐方案和用户历史裁决做出最佳推断，标注冲突及处理方式。
   - 若有可复用项 → 默认复用已有契约（用户历史裁决优先）。
   - 若用户历史裁决与 harmonizer 推荐冲突 → **以用户裁决为准**。
3. **生成落地规范对外接口章节**（【已锁定】）：
   - 1.3 输入定义（契约引用格式）
   - 1.4 输出定义（契约引用格式）
   - 1.6 接口契约（完整函数签名、docstring、异常、副作用）
   - 1.7 依赖与集成接口
   - 对外接口类型使用契约引用，不写完整字段定义。
4. **生成落地规范内部实现章节**（【对内实现】）：
   - 1.1 技术栈绑定 → 1.2 文件归属
   - 1.5 核心逻辑步骤（原子操作，含操作对象、输入来源、输出去向、失败行为）
   - 1.8 状态机（表格形式，如适用）
   - 1.9 异常与边界条件（≥3 种，含精确触发阈值、处理策略、重试参数）
   - 1.10 验收测试场景（≥2 正 + 2 异常，Given-When-Then + 完整 JSON）
   - 1.11 注意事项与禁止行为（编码层面）
   - 1.12 文档详细度自检清单
   - 1.13 意图一致性声明
   - 1.14 外部接口契约清单
   - 模板：`references/agent-spec-template.md`
5. **写入契约文件**：
   - 将对外类型写入 `docs/contracts/{module_id}/`。
   - 格式必须符合 `references/contract.schema.json`。
   - `x-defined-by` 填写本模块编号，`x-maturity` 初始为 `draft`。
   - 复用已有契约的类型 → 不新建文件，在 `_module-index.json` 中记录 `reference_only: true`。
   - 目录结构参考 `references/contract-directory-guide.md`。
6. **更新索引**：
   - 更新 `docs/contracts/_index.json`：追加本模块契约条目，更新 `x-consumers`。
   - 更新 `docs/功能设计/_contracts.md`：按模块编号插入/更新条目。
   - 格式参考 `references/contract-index-template.md`。
   - 时间戳通过工作流级共享脚本 `scripts/get_timestamp.py` 获取。
7. **输出落地规范**：
   - 合并对外接口章节和内部实现章节，输出到 `docs/功能设计/[分组]/[编号]-[名称]/[编号]-[名称]-落地规范.md`。
   - 对外接口章节标记 `【已锁定】`，内部章节标记 `【对内实现】`。
8. **上报**：按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `report` 包含：落地规范路径、契约文件清单、索引更新状态、冲突处理说明（如有）。
   - `confirm_questions` 示例：
     - "落地规范的对外接口定义是否准确？"
     - "契约冲突处理方案（如有）是否可接受？"
     - "内部实现逻辑、异常处理、验收测试是否满足要求？"
   - 确认通过 → 流转到 s16 同步检查。
   - 拒绝 → s15→s15 循环修订（max_loop: 3，见 WORKFLOW.yaml）。

### s16-module-sync-check：模块级同步检查（cp:true）

**目标**：检查项目级同步问题记录，汇报矛盾情况供用户决策。

1. **读取同步问题**：读取 `docs/功能设计/_sync-issues.md` 中与本次模块周期相关的条目。
2. **汇总矛盾情况**：
   - 列出本模块引入的新增冲突。
   - 列出本模块发现但未解决的遗留冲突。
   - 若无问题 → 标注"✅ 本模块未引入同步矛盾"。
3. **上报**：按 agent-protocol.md 的确认点规范上报 `PENDING_CONFIRM`：
   - `confirm_questions` 示例：
     - "以上同步矛盾是否需要在进入下一模块前处理？"
     - "是否继续选择下一模块（若选择'否'则终止工作流）？"
   - 确认通过 → 流转到 s06 选择下一模块。
   - 拒绝 → 流转到 s99 工作流终止（见 WORKFLOW.yaml）。

## 回退机制

> **硬性约束：发现意图缺陷时，无权自行妥协。**

**触发条件**（满足任一）：
1. 意图文档中的业务约束或验收标准在当前技术架构下**不可能实现**
2. 意图文档中的要求与项目技术栈设计文档存在**不可调和的冲突**
3. 意图文档中"留给规范阶段的技术决策"清单不完整，缺少关键技术决策项
4. 意图文档中的业务规则存在**逻辑矛盾**，无法转化为一致的技术实现

**回退流程**：
1. **立即停止当前所有工作**，不得继续生成设计文档或落地规范。
2. 上报 `ERROR`，`report` 中必须包含：
   - 标记为 **"意图缺陷"**
   - 缺陷内容（引用意图文档的具体章节和原文）
   - 技术不可行的依据
   - **回退路径**："请使用 module-intent-writer 回退到意图文档阶段，修正以下缺陷后重新冻结：\n- [缺陷描述]\n修正后重新冻结意图文档，再进入规范阶段。"

**禁止行为**：
- 禁止发现意图缺陷后自行修改或妥协
- 禁止绕过意图缺陷继续生成文档
- 禁止将意图缺陷隐藏在设计文档的注释中

## 质量检查清单

输出前逐项确认：

**通用检查**：
- [ ] 意图文档已存在且已冻结
- [ ] 无未解决的意图缺陷（回退机制未触发或已处理）
- [ ] 两份文档的模块编号、名称、版本记录保持一致
- [ ] 所有"（待确认）"标注都有合理推断
- [ ] 已参考项目技术栈设计文档
- [ ] 版本记录每行以 `> ` 开头（引用块内）

**设计文档检查**（s13 产出）：
- [ ] 聚焦"为什么这样实现"，非罗列步骤
- [ ] 架构权衡有具体方案对比和选择理由
- [ ] 不包含业务定位、用户旅程、验收标准、业务约束
- [ ] 依赖关系概述精确到框架/服务/协议

**落地规范检查**（s15 产出）：
- [ ] 对外接口类型已转为契约引用，不写完整字段定义
- [ ] 契约文件已写入 `docs/contracts/{module_id}/`，格式符合 contract.schema.json
- [ ] 异常场景 ≥ 3 种，每种含精确触发阈值、处理策略、重试参数
- [ ] 验收测试 ≥ 2 正 + 2 异常，Given-When-Then + 完整 JSON
- [ ] 依赖声明具体到函数名/Cypher 查询/类名
- [ ] 状态机使用表格形式（如涉及）
- [ ] 无偷懒表述（"等等"、"..."、"其他字段"、"参考其他模块"）
- [ ] 文档自包含：不了解代码的 Agent 可凭此文档独立完成编码
- [ ] 包含"意图一致性声明"和"外部接口契约清单"章节

**契约文件检查**（s15 产出）：
- [ ] `x-defined-by` 已正确填写为本模块编号
- [ ] `x-contract-type` 已正确标注
- [ ] 与已有契约的冲突已解决（以用户裁决为准）
- [ ] `docs/contracts/_index.json` 已更新
- [ ] `docs/功能设计/_contracts.md` 已更新
